# 05 单词统计

一个统计文本文件单词数的命令行工具，逐个字符扫描，用状态机判定单词边界。

## 功能

```bash
./bin/count a.txt b.txt
      14 a.txt
  114588 b.txt
```

- 支持一次传入多个文件，逐个输出词数
- 文件打不开或读取失败时输出错误原因到 stderr，退出码非 0
- 无参数时输出用法提示

## 核心实现

### 状态机

判定"是否处于单词内部"只需要两个状态：

```c
enum { OUT = 0, IN = 1 };

int status = OUT;
while ((c = fgetc(fp)) != EOF) {
    if (is_separator(c)) {
        status = OUT;
    } else if (status == OUT) {
        status = IN;
        word++;
    }
}
```

关键在于**只在 `OUT -> IN` 的那一次跳变上计数**。这样每个单词恰好被计一次，
不需要记录上一个字符，也不需要判断"是否是最后一个字符"。额外空间是 O(1)，
与文件大小无关，不需要把文件读进内存。

`IN -> IN`（单词中途）和 `IN -> OUT`（单词结束）都不计数：前者是同一个单词的
延续，后者已经在上一次跳变时计过了。

同样的思路在 `wc`、词法分析器的扫描器、以及各类流式统计里都是标准做法。

### 分隔符的判据

判据定义为"不是字母数字"：

```c
static int is_separator(int c) {
    return isalnum(c) == 0;
}
```

也就是 **单词 = 最长的连续字母数字段**。这等价于常说的一句"分隔符 = 空白或标点"，
但对 ASCII 而言，字母数字的补集除了空白和标点，**还包含控制字符和 0x80 以上的
高位字节**。这一点在 UTF-8 文本上有实际影响，见下文"已知局限"。

原版代码用的是手写字符表：

```c
if ((' ' == c) || ('\n' == c) || ('\t' == c) ||
        ('\"' == c) || ('\'' == c) || ('+' == c) ||
        (',' == c) || ';' == c || '.' == c)
    return 1;
```

这张表只覆盖了 9 个字符，`! ? - ( ) [ ] { } : / = < > | @ # $ % ^ & * ~ \`` 等
全部漏掉。`a.txt` 就是为暴露这一点准备的测试数据，里面含 `!`、`{`、`-+`、`}`：

```
Foreword.
 After several ' " ; , . ! { -+  } years of contemplation and of thought upon the matter herein contained,
```

用原版的表统计 `a.txt` 得到 18，用 `isalnum` 判据得到 14。差出来的正是
`!`、`{-`、`}` 这些被漏掉的标点所连成的"词"。

## 编译与运行

```bash
mkdir -p bin
gcc -std=c11 -Wall -Wextra -Wconversion -O2 count.c -o bin/count
./bin/count a.txt b.txt
```

建议编译参数说明：

| 参数 | 作用 |
|---|---|
| `-std=c11` | 固定语言标准，避免依赖编译器的默认方言 |
| `-Wall -Wextra` | 常规警告集 |
| `-Wconversion` | 检查隐式窄化转换，本主题最关键的一处缺陷只有它能发现 |
| `-O2` | 优化；本程序不依赖任何未定义行为，优化不会改变结果 |

消毒剂验证：

```bash
gcc -std=c11 -Wall -Wextra -O0 -g -fsanitize=address count.c -o bin/count_asan
./bin/count_asan a.txt b.txt
```

## 原版的缺陷与修复

### 1. `char c` 接收 `fgetc` 的返回值

```c
char c;
while ((c = fgetc(fp)) != EOF) {
```

这是本主题最重要的一处。C11 7.21.7.1 规定 `fgetc` 的返回类型是 `int`，
读到文件末尾或出错时返回 `EOF`（一个负值）。而 C11 6.2.5p15 规定
**`char` 是否有符号由实现决定**。

- 在 x86 上 `char` 有符号，`-1` 能存进去，比较 `!= EOF` 成立，程序看起来正常。
- 在 ARM 等平台上 `char` 默认**无符号**，`EOF`（-1）被截断成 255，
  与 `EOF` 永远不相等。循环条件恒为真，读取越界后 `fgetc` 持续返回 `EOF`，
  每次又都被截断成 255，**进程陷入死循环**。

用 `-funsigned-char` 模拟无符号平台，实测确认：

```
$ timeout 3 ./count_uchar a.txt
退出码=124
>>> 超时：进程陷入死循环
```

GCC 在无符号 `char` 下会给出警告（`-Wtype-limits` 属于 `-Wextra`）：

```
count.c:30:32: warning: comparison is always true due to limited range of data type [-Wtype-limits]
```

而在**有符号 `char`（x86 默认）下这条警告不会出现**，`-Wall -Wextra` 也不报任何东西；
只有 `-Wconversion` 能发现类型不匹配：

```
count.c:30:21: warning: conversion from 'int' to 'char' may change value [-Wconversion]
```

修复是把 `c` 声明为 `int`。这还有第二个作用：C11 7.4p1 规定传给 `ctype`
系列函数的值要么等于 `EOF`，要么可表示为 `unsigned char`，传负的 `char`
属于未定义行为。用 `int` 同时满足比较和调用两个场景。

### 2. 缺少 `fclose`，文件描述符泄漏

原版 `count_word` 在 `fopen` 之后，任何一条返回路径都没有 `fclose`：

```c
int count_word(char *filename) {
    FILE *fp = fopen(filename, "r");
    if (fp == NULL) return -1;
    /* ... 扫描 ... */
    return word;              /* fp 从未关闭 */
}
```

写一个测试程序把 `count_word` 连续调用 500 次，统计 `/proc/self/fd`：

```
原版    : 起始 3 → 调用后 503，净增 500 个文件描述符
完善版  : 起始 3 → 调用后 3  ，净增 0 个文件描述符
```

本机 `ulimit -n` 为 1024，也就是说原版在同一个进程里累积约 520 次调用后，
`fopen` 就会因 `EMFILE` 失败。

注意在一次性小程序里这个缺陷不会暴露——`main` 调用一次就退出，进程结束
时内核统一回收描述符。但只要这个函数被放进长期运行的循环（例如为守护进程
统计轮转日志），泄漏立刻变成硬故障。**所有权应当明确：`fp` 在本函数内
`fopen`，就由本函数在每一条返回路径上关闭。**

修复后同时补了 `ferror` 检查——`fgetc` 返回 `EOF` 有两种可能（正常读完、
发生读错误），只看 `EOF` 会把读错误当成正常结束：

```c
if (ferror(fp)) {
    int e = errno;      /* 先取出 errno，因为 fclose 可能改写它 */
    fclose(fp);
    return e;
}
if (fclose(fp) != 0) {
    return errno;       /* fclose 自身也可能失败，例如延迟写时磁盘满 */
}
```

### 3. 不检查返回值，错误被当成正常结果

```c
printf("word: %d\n", count_word(argv[1]));
```

`count_word` 在文件打不开时返回 -1，而原版直接把它当词数打印：

```
$ ./count_orig nosuch.txt
word: -1
```

用户看到的是"这个文件的词数是 -1"，而不是"文件打不开"。完善版改为返回
`errno`，由 `main` 输出可读原因，并让退出码反映失败：

```
$ ./bin/count nosuch.txt ; echo "退出码=$?"
count: nosuch.txt: No such file or directory
退出码=1
```

退出码是关键：脚本里用 `if ./bin/count "$f"; then` 或 `&&` 串联时，
原版永远返回 0，失败无法被检测到。

### 4. 只能处理单个文件，无参数时静默退出

原版 `argc < 2` 时直接 `return -1`，不给任何提示，用户不知道哪里出了问题。
完善版输出用法并遍历 `argv[1..argc-1]`：

```c
if (argc < 2) {
    fprintf(stderr, "usage: %s <file> [file ...]\n", argv[0]);
    return 1;
}
```

### 5. 计数器使用 `int`

`int` 在常见平台上上限是 2147483647。本主题的 `b.txt` 是 617 KB、约 11.5 万词；
把 20 份拼成 12.35 MB 后是 229 万词，还不至于溢出，但处理超大文本时
（如语料库、日志聚合）会撞上上限。改用 `long`，在 64 位 Linux 上是 64 位。

### 6. 不是缺陷：`main` 缺少 `return`

原版的 `main` 走到 `}` 结束，没有 `return` 语句。这**不构成缺陷**：
C11 5.1.2.2.3 专门规定，`main` 执行到终结的 `}` 等价于执行 `return 0;`。
这是标准为 `main` 开的特例，其他函数不享有。

有一个可观测的旁证很有意思：把 `main` 改名之后，GCC 立刻开始报警告——

```
$ gcc -Wall -Wextra -Dmain=count_main_orig -c count.c -o /dev/null
count.c:52:1: warning: control reaches end of non-void function [-Wreturn-type]
```

因为在它眼里这已经不是 `main` 了，特例不再适用。这也解释了原版在
`-Wall -Wextra` 下**完全零警告**的部分原因。完善版仍然显式写了 `return failed;`，
因为它的返回值承载了"是否有文件处理失败"的信息，本来就该写出来。

### 7. 其他

- 函数名 `splite` 是 `split` 的拼写错误，改为 `is_separator`（同时也更准确：
  这个函数判断的正是"是不是分隔符"，不是"切分"）
- `#define OUT 0` / `#define IN 1` 改为 `enum`，名字有类型、调试器可见，
  且不会被预处理阶段无差别替换
- `splite` 与 `count_word` 改为 `static`，把符号限制在本编译单元内，
  避免与将来其他文件里的同名函数冲突

## 验证结果

环境：Linux 6.8 / gcc 11.4.0 / x86_64，测试数据 `a.txt`（118 字节）、
`b.txt`（617637 字节，1762 行）。

### 编译警告

| 编译参数 | 原版 | 完善版 |
|---|---|---|
| `-std=c11 -Wall -Wextra` | 0 条 | 0 条 |
| 追加 `-Wconversion` | 1 条（`int`→`char` 窄化） | 0 条 |
| `-funsigned-char -Wextra` | 1 条（`-Wtype-limits`） | 0 条 |

### 正确性交叉验证

用一条与程序完全无关的路径独立计算词数，两者应精确一致：

```bash
tr -c '[:alnum:]' '\n' < 文件 | grep -c '[[:alnum:]]'
```

原理：把所有非字母数字的字节替换成换行，再数非空行数，即"最长连续字母数字段"的个数。

| 文件 | 本程序 | 独立方法 | 结论 |
|---|---|---|---|
| `a.txt` | 14 | 14 | 一致 |
| `b.txt` | 114588 | 114588 | 一致 |

### 边界用例

| 输入 | 内容 | 本程序 | 独立方法 |
|---|---|---|---|
| `t_empty.txt` | 空文件（0 字节） | 0 | 0 |
| `t_sep.txt` | 只有空白与制表符、换行，无任何字母数字 | 0 | 0 |
| `t_one.txt` | 单个单词，不带结尾换行 | 1 | 1 |
| `t_nonl.txt` | `hello world`，不带结尾换行 | 2 | 2 |

第 3、4 条值得单独说明：**按 `OUT -> IN` 跳变计数的设计天然处理了"文件末尾没有换行符"的情形。**
如果反过来按 `IN -> OUT` 跳变计数（"遇到分隔符时结算上一个单词"），
文件以字母数字结尾、后面没有分隔符时，最后一个单词就永远不会被结算。
这是状态机计数方向的选择问题，不是边界条件的补丁问题——选错方向要多写一段
"循环结束后再判一次"的收尾代码。

### 三种词数口径的对照

同一份 `b.txt`，按不同的"单词"定义得到不同结果。列出这组数据是为了说明
**词数不是唯一确定的量，取决于定义**：

| 定义的"单词" | 实现方式 | b.txt 结果 |
|---|---|---|
| 非空白段 | `wc -w` | 113550 |
| 非（空白或标点）段 | 原版设计意图，`isspace \|\| ispunct` | 115426 |
| 字母数字段 | 本程序，`isalnum` | 114588 |

第二种比第三种多出 838 个"单词"，原因见"已知局限"。

### 消毒剂与资源验证

| 验证项 | 原版 | 完善版 |
|---|---|---|
| ASan（越界、泄漏） | 未跑 | 无报告 |
| 文件描述符泄漏（500 次调用） | 净增 500 | 净增 0 |
| 无符号 `char` 平台（`-funsigned-char`） | 死循环（超时） | 正常退出，结果正确 |
| 不存在的文件 | 打印 `word: -1` | 报错到 stderr，退出码 1 |

## 性能

测试数据：把 `b.txt` 拼接 20 份得到的 `big.txt`，12.35 MB，共 2291760 词。
每个组合跑 5 轮取总时间，`-O2` 编译：

| 实现 | 5 轮总耗时 | 单轮 | 吞吐 |
|---|---|---|---|
| 原版（`fgetc`，`int` 未修） | 0.425 s | 85 ms | 145 MB/s |
| 完善版（`fgetc`） | 0.400 s | 80 ms | 154 MB/s |
| 完善版改 `getc_unlocked` | 0.393 s | 79 ms | 157 MB/s |
| `wc -w`（参考） | 0.274 s | 55 ms | 225 MB/s |

两个结论：

1. **完善版没有引入性能退化**，反而略快（`isalnum` 是一次表查找，
   原版的链式字符比较在字符落在表尾时反而更慢）。
2. **`getc_unlocked` 不值得用。** 它去掉 stdio 的每字符加锁，
   实测只快约 2%，落在噪声区间内。而它是 POSIX 扩展、不是 C 标准的一部分，
   代价是多一个平台依赖。**这就是典型的过早优化**——先测量，再决定要不要改。

`wc` 比本程序快约 45%，因为它内部使用更大的读取块并做了更激进的优化。
本程序是逐字符扫描的教学实现，可读性优先，这个差距可以接受。

## 已知局限

### 非 ASCII 字节被当作分隔符

本程序是**字节导向**的，并且使用 C locale。在 C locale 下，`isalnum`
对 0x80–0xFF 一律返回 0，因此这些字节全部被当作分隔符。

这带来两个后果，方向相反：

- **好的一面**：孤立的 UTF-8 标点不会被误计成单词。`b.txt` 中含
  8757 个非 ASCII 字节（正文使用了 UTF-8 弯引号 `"" ''`，其中 `""` 共 2482 个、
  `'` 共 322 个）。如果判据用 `isspace || ispunct`，这些字节既不是空白也不是
  标点，会被当成"词字符"，于是一个孤零零的弯引号就成了一"个单词"——
  实测会凭空多出 838 个这样的词。
- **不好的一面**：弯撇号会被切开。`don't` 写作 `don’t` 时，撇号是 3 个
  高位字节，全部被当作分隔符，于是算成 2 个词。

**严格的 UTF-8 处理需要另一套做法**：用 `setlocale(LC_ALL, "")` 打开区域设置，
用 `mbrtowc` 把字节流转换成宽字符，再用 `iswalpha` 判断——这是"按字符"而非
"按字节"扫描，代码量和复杂度都会明显上升。本主题的定位是字节流扫描的基础实现，
不展开。

### 大小写不敏感的词频统计未实现

当前只输出总数。若要统计每个词出现的频次（即 `wc` 之外更像 `sort | uniq -c` 的场景），
需要一个"单词 -> 计数"的映射表。在 C 里通常用哈希表实现，涉及哈希函数设计、
冲突处理、内存管理，是另一个量级的话题。

### 只支持普通文件

`fopen` 在 Linux 上也能打开目录，但随后的 `fgetc` 会返回错误（`EISDIR`）。
完善版会通过 `ferror` 报出 `Is a directory`，但不会预先把目录识别出来并
给出更准确的提示。
