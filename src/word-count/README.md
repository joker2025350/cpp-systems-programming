# 05 单词统计（wordcount 模块）

一个可复用的文本统计模块，加一个建立在它之上的命令行驱动。

模块对字节流做单遍扫描，统计行数、单词数与字节数。核心是 `wc_counter` 这个流式计数器：
它把扫描状态与累计结果封装在对象里，因此同一份数据无论被切成多少段送入，结果都完全一致。
`include/` 与 `src/` 分离，`main.c` 只通过 `libwordcount.a` 链接，不重复编译模块源码——
"这个模块能被独立链接使用"这件事在每次构建时都会被动验证一遍。

驱动层还多走了一步：`-j N` 时把每个输入拆成"某个文件的一个字节区间"——不小于 2 MiB 的
普通文件按分隔符对齐切成若干段，其余文件整份一个任务——全部任务进同一个队列，按字节数
从大到小提交，由 `src/thread-pool` 的线程池执行。**库本身不引用线程池，也不引用 pthread**，
依赖方向只有一条：驱动 → `libthreadpool.a`；`libwordcount.a` 的使用者不必链接线程。

```bash
$ ./bin/wordcount testdata/a.txt testdata/b.txt
       2       14      118 testdata/a.txt
    1762   114588   617637 testdata/b.txt
    1764   114602   617755 total

$ ./bin/wordcount -j 4 logs/*.log     # 四个文件并行，输出与不加 -j 时逐字节相同
$ ./bin/wordcount -j 8 huge.log       # 单个大文件切成 8 段并行，输出同样逐字节相同
$ ./bin/wordcount -j 8 huge.log *.log # 大文件切段、小文件整份，共用一条队列
```

## 2 对外接口

### 2.1 统计结果

```c
typedef struct {
    unsigned long lines;   /* '\n' 出现的次数 */
    unsigned long words;   /* 最长连续字母数字段的个数 */
    unsigned long bytes;   /* 已扫描的字节总数 */
} wc_stat;
```

三个计数都是单调递增的累计量，没有负数，因此用无符号类型。`unsigned long` 在 LP64 平台
（Linux x86-64 / AArch64）上是 64 位，足够覆盖任何实际文件；在 32 位平台上上限约 42.9 亿，
若要处理更大的输入需要改用 `uintmax_t`。

### 2.2 状态码

```c
typedef enum {
    WC_OK         = 0,   /* 成功 */
    WC_ERR_PARAM  = 1,   /* 参数非法，例如传入了 NULL */
    WC_ERR_OPEN   = 2,   /* 无法打开文件 */
    WC_ERR_READ   = 3,   /* 读取过程中出错 */
    WC_ERR_CLOSE  = 4    /* 关闭文件时出错 */
} wc_status;
```

沿用 C 语言的惯例：0 表示成功，非 0 表示失败。`WC_OK` 固定为 0，因此可以直接写
`if (status)` 判断失败。返回后三种错误时 `errno` 保留导致失败的系统错误号，
调用方可以据此给出更具体的信息；返回 `WC_ERR_PARAM` 时 `errno` 无意义。

一个模块如果只用 `-1` 表示"出错了"，调用方就没法区分"文件不存在"和"读到一半磁盘坏了"，
只能自己猜。把错误分类是接口设计的一部分，不是附加功能。

### 2.3 流式计数器

```c
typedef struct {
    unsigned int state;    /* 内部：上一次扫描结束时的入/出词状态 */
    wc_stat      total;    /* 累计结果 */
} wc_counter;
```

这是模块的核心。结构体成员是公开的，为的是让调用方能在栈上直接分配、不必走
`malloc`——嵌入式环境下不希望在读一个文件时还依赖堆。但约定调用方不直接读写字段，
一切通过下面的函数。

### 2.4 函数

| 函数 | 作用 |
|---|---|
| `void wc_counter_reset(wc_counter *c)` | 把状态与三个累计量全部归零 |
| `wc_status wc_counter_update(wc_counter *c, const void *data, size_t size)` | 把一段字节追加到计数器 |
| `void wc_counter_get(const wc_counter *c, wc_stat *out)` | 取出当前累计结果（值拷贝） |
| `wc_status wc_count_buffer(const void *data, size_t size, wc_stat *out)` | 统计一段内存，等于 reset + update + get |
| `wc_status wc_count_stream(FILE *stream, wc_stat *out)` | 统计一个已打开的流，读到文件末尾，不关闭 stream |
| `wc_status wc_count_file(const char *path, wc_stat *out)` | 统计一个文件，内部负责关闭句柄 |
| `wc_status wc_align_chunk(int fd, off_t from, off_t limit, off_t *out)` | 把"建议切点"调整成"合法切点"，即 ≥ `from` 的第一个分隔符偏移 |
| `wc_status wc_count_fd_range(int fd, off_t from, off_t to, wc_stat *out)` | 统计 fd 上 `[from, to)` 这段字节（`pread`，不动文件偏移量） |
| `const char *wc_status_string(wc_status status)` | 状态码转可读描述，未知值返回 `"unknown status"` |

按使用场景分三层：

- **已经有完整数据**（mmap 映射、网络收包缓冲、字符串常量）→ `wc_count_buffer`
- **自己在驱动 I/O**（socket、管道、分块解压）→ `wc_counter` + `wc_counter_update`，按任意粒度喂
- **就是读个文件** → `wc_count_file` 一行搞定
- **要自己把一个大文件拆给多个线程** → `wc_align_chunk` 算切点，`wc_count_fd_range` 数每一段

### 2.5 缓冲区大小

```c
#ifndef WC_BUFFER_SIZE
#define WC_BUFFER_SIZE 16384u
#endif
```

只被 `wc_count_stream` / `wc_count_file` 使用。用 `#ifndef` 包一层，是为了允许在编译命令上
用 `-DWC_BUFFER_SIZE=n` 覆盖——没有这层保护，命令行传入的定义会被头文件里的 `#define` 覆盖掉，
结果是改了没效果而且不报错。取值取舍见第 6 节。

### 2.6 可重入性与线程模型

模块不使用任何全局状态，也没有内部的静态缓冲区，因此同一个进程里可以同时持有任意多个
互相独立的计数器。只要不同线程各自使用自己的 `wc_counter` 对象，并发调用是安全的；
`FILE *` 自身的并发访问按 stdio 的约定由调用方负责。

这条约束直接来自"状态外置"这个设计决定：状态如果在函数里用 `static` 变量保存，
这个模块就只能有一个实例，也没法在多线程里用。

### 2.7 跨模块依赖：只有驱动层用 thread-pool

`src/main.c` 的 `-j` 选项要把输入拆成任务并并发处理，用的是 `src/thread-pool` 的
`include/threadpool.h`；而 `libwordcount.a` 里没有任何对 `threadpool_*` 的引用。

方向是刻意单向的：

```
src/main.c  ──►  libwordcount.a      （统计逻辑）
    └─────────►  libthreadpool.a     （任务调度）
libwordcount.a ──► （无外部依赖，不需要 pthread）
```

理由：并发是"怎么调度 I/O 与 CPU"，不是"怎么数词"。把线程池塞进库里，
等于要求每个使用者都接受 pthread、都能接受库在后台建线程；而只想数一个文件的调用方，
本来只需要 `fopen` + `fread`。头文件 `wordcount.h` 因此连 `<pthread.h>` 都不出现。

代价是驱动层必须同时链接两个静态库，`Makefile` 里多了一条把 thread-pool 建到
本模块 `bin/` 下的规则（见第 4 节）。这属于把耦合点收到一处，而不是消灭它——
能看见的耦合比藏起来的耦合好处理。

### 2.8 按区域切分：`wc_align_chunk` 与 `wc_count_fd_range`

1.1.0 新增的一对函数，只做"找边界"与"数一段"，**不创建线程**：

```c
wc_status wc_align_chunk(int fd, off_t from, off_t limit, off_t *out);
wc_status wc_count_fd_range(int fd, off_t from, off_t to, wc_stat *out);
```

`wc_align_chunk` 从 `from` 往后找第一个分隔符字节，把它的偏移写进 `*out`；
`[from, limit)` 里一个分隔符都没有时写 `limit`，表示"这段没有可用切点"。
`wc_count_fd_range` 统计 `[from, to)`，用的是 `pread` 而不是 `FILE *`。

**为什么是 `pread`。** POSIX 对 `pread` 的语义有明文规定：它按绝对偏移读写，
不改变文件偏移量，也不受其他线程对该 fd 的读写影响（`read` 则会移动共享的文件偏移量，
两个线程同时 `read` 同一个 fd 会各拿到一段不完整的数据）。因此同一 fd 可以被多个线程
并发读不同区域，一个字都不用锁。这条依赖是 POSIX 专有的，Windows 上没有等价物——
但这个模块本来就只面向 Linux。

**`errno` 为 0 表示什么。** `wc_count_fd_range` 在"还没读到 `to` 就到了文件末尾"时返回
`WC_ERR_READ` 并把 `errno` 显式清零。这不是系统调用失败，而是文件在统计期间被截短；
调用方若直接 `strerror(errno)` 会拿到 `"Success"`，反而误导。把 `errno` 清成 0 让两种情况
在返回值上同类（都是 `WC_ERR_READ`）、在 `errno` 上可区分。

**参数错误时不修改 `*out`。** 两条函数都遵守这一点，`tests/test_split.c` 有对应断言
（把 `out` 预置成 7 或 -1，调用失败后检查它没被改）。理由是调用方常在同一个变量上重试，
"失败也写了一半"会让重试路径拿到脏值。

## 3 设计要点

### 3.1 状态机：只在 `OUT -> IN` 跳变上计数

判定"是否处于单词内部"只需要两个状态：

```c
enum { WC_STATE_OUT = 0, WC_STATE_IN = 1 };

for (size_t i = 0; i < size; i++) {
    unsigned char ch = p[i];
    if (ch == '\n') lines++;
    if (wc_is_separator(ch)) {
        state = WC_STATE_OUT;
    } else if (state == WC_STATE_OUT) {
        state = WC_STATE_IN;
        words++;
    }
}
```

关键在于只在 `OUT -> IN` 的那一次跳变上计数：每个单词恰好被计一次，不需要记录上一个字符，
也不需要判断"是不是最后一个字符"。额外空间是 O(1)，与输入规模无关。

`IN -> IN`（单词中途）和 `IN -> OUT`（单词结束）都不计数：前者是同一个单词的延续，
后者已经在上一次跳变时计过了。

**计数的方向是有代价的。** 如果反过来按 `IN -> OUT` 跳变计数（"遇到分隔符时结算上一个单词"），
那么当输入以字母数字结尾、后面没有分隔符时，最后一个单词永远不会被结算——必须额外写一段
"循环结束后再判一次收尾"的代码。而 `OUT -> IN` 天然处理了这种情况，测试用例
`单个单词，无结尾换行` 就是为了盯住这一点。这是状态机计数方向的选择问题，不是边界条件的补丁问题。

### 3.2 状态外置：流式处理的必要条件

`state` 存在 `wc_counter` 对象里，而不是 `wc_counter_update` 的局部变量里。这是整个模块
能做到"任意粒度切分结果一致"的原因。

反例很直观：一段文本分两次送入，第一次以 `hel` 结束，第二次以 `lo` 开始。状态若在函数退出时
丢失，第二次送入 `l` 时看到的局部状态是 `OUT`，于是把这个词的后半段当成一个新词，
结果从 1 变成 2。`wc_counter_update` 在每次调用结束时把 `state` 写回对象，下次调用接着用，
所以两条边界合起来仍然只算一个词。

`tests/test_wordcount.c` 里的 `test_chunk_boundary` 把 `"hello world"` 按 1 到 11 字节
共 11 种粒度逐一切分送入，结果都必须与整体送入一致；`test_split_inside_word` 则专门在词中间
切断一次。这两组用例覆盖的正是单文件 demo 最容易忽略、而任何真正要处理流的模块必须处理的场景。

### 3.3 参数与所有权约定

接口上写清楚了三件事，代码里逐一落实：

1. **`data` 允许为 NULL，此时 `size` 必须为 0**（表示一段空输入）。C11 6.5.6p8 规定，
   对空指针做算术运算（包括 `p + 0`）是未定义行为，所以 `data == NULL && size != 0` 要拒掉，
   `data == NULL && size == 0` 则要在进入循环之前就返回，不能先去构造 `const unsigned char *p = data`。
2. **返回 `WC_ERR_PARAM` 时计数器内容不被修改**。调用方可以放心重试，不必先存档。
3. **`wc_count_file` 内部 `fopen`，就由它负责在每一条返回路径上 `fclose`。** 所有权跟着作用域走，
   不依赖调用方记得清理。

### 3.4 `errno` 的保存与恢复

```c
wc_status status = wc_count_stream(fp, out);
int saved = errno;                                    /* 先存 */
if (fclose(fp) != 0 && status == WC_OK) {
    return WC_ERR_CLOSE;
}
errno = saved;                                        /* 后恢复 */
return status;
```

`fclose` 会刷新 stdio 缓冲区、可能触发实际的 `write` 系统调用，因此它**可能改写 `errno`**。
如果先 `fclose` 再读 `errno`，读到的可能是关闭阶段产生的错误号，把真正的读错误覆盖掉；
如果 `fclose` 成功，它还可能把 `errno` 改成一个与本次失败无关的残留值。

顺序必须是"先存、后调 `fclose`、再恢复"。这两行看着不起眼，但少了任何一行，
错误信息都会在小概率下指向错误的原因——而 `errno` 相关的问题做压力测试很难复现。

### 3.5 语义明确定义在头文件里

`lines` 定义为 `'\n'` 出现的次数，不是"文本行数"。区别在于最后一行若没有换行符，
不计入行数；空行则计入。这个选择与 `wc -l` 一致，因此可以直接交叉验证。
如果把它定义成"文本行数"，`a\nb\nc` 到底算 2 行还是 3 行就会成为接口层面的争议，
而实现方无论选哪个都要在文档里解释半天。跟随已有的、有明确定义的工具，是最省事的选择。

### 3.6 并行驱动：任务划分、提交顺序与输出顺序

**任务单元是"某个文件的一个字节区间"，不是"一个文件"。** `-j N` 时驱动分两段走：

1. **规划**：按 argv 顺序逐个文件 `open` + `fstat`。不小于 2 MiB 的普通文件按 3.7 节的
   规则对齐切段（每段不小于 1 MiB、每个文件不超过 `jobs × 4` 段），每段一个任务，
   fd 保持打开供任务用 `pread`；其余文件（太小、非普通文件、`-j < 2`）整份一个任务，
   任务里按路径重新打开、用 stdio 读到 EOF。
2. **执行**：两类任务进同一个池，池里没有优先级也没有分桶；全部完成后主线程按 argv
   顺序输出。

规划与执行分开的直接原因是：任务总数必须在建池之前已知，线程数才能取
`min(JOBS, 任务数)`。

**为什么单按文件切不够。** 一个文件一个任务时，总时长由最大的那个文件决定。
8 个工作线程、8 个文件，其中一个是 64 MiB、其余各 1 MiB：7 个线程几十毫秒后就空了，
wall 时间等于 64 MiB 的单线程耗时。这不是估算——6.7 节把 `-j 1 huge.txt` 当
"老实现的地板"直接量出来做对照。反过来说，"文件之间天然独立、不需要任何同步"
这个优点并没有丢：区间任务之间同样独立，只是把独立单位从文件细到了字节区间。

**为什么单按区间切也不够。** 段数被两条约束夹住：每段不小于 1 MiB、
每文件不超过 `jobs × 4` 段。文件数远多于线程数时并行度早已饱和，再给每个小文件
切段只是多一份规划开销与一个长期打开的 fd。所以门槛以下（小于 2 MiB）的文件
整份一个任务。

**提交顺序按任务字节数降序（LPT，longest processing time first）。** 队列表调度的
完工时间上界是 `4/3 - 1/(3m)`（m 为工作线程数），前提正是降序提交。若按 argv 顺序提交，
末尾剩一个大任务时其余线程只能空转，最坏退化成单线程——那正是"按文件分发"的老问题，
只是从文件级挪到了区间级。区间长度已经等价于耗时（扫描是 CPU 密集的，单位字节成本
在一次运行内基本恒定），所以一次 `qsort` 就够，不需要真正的调度器。等长任务的次序
按 `(文件下标, 段号)` 定死：`qsort` 不保证稳定，只比长度会让提交次序依赖 libc
（glibc 的归并排序与 musl 的平滑排序结果不同），排障时无法复现。

**输出顺序为什么必须由主线程决定。** 如果任务函数自己 `printf`，行序取决于
哪个区间先读完：同一批文件跑两遍，行序可能都不一样。这类差异肉眼很难发现
（数字全对），却会让任何基于 `diff` 的脚本失效。本实现让每个任务只往自己那个
槽位里写结果，主线程在 `threadpool_wait` 之后按 argv 顺序统一打印：

```c
typedef struct {
    const char *path;
    int         kind;          /* 整文件 / 一个字节区间 */
    int         fd;            /* 区间任务用的 fd，规划阶段打开 */
    int         file;          /* 所属文件在 entries[] 里的下标 */
    int         seg;           /* 文件内的段号 */
    off_t       from, to;      /* 区间，长度就是调度权重 */
    int         submitted;
    wc_status   status;
    int         saved_errno;   /* 在任务线程内部取，不能回到主线程再读 */
    wc_stat     stat;
} seg_task;
```

槽位数 = 任务数，一个槽位只由一个任务写。**并发代码最省事的写法是不让它共享
可写状态**：没有共享，就没有数据竞争，也没有锁——这也是 TSan 保持干净的原因。

**`errno` 必须当场取值。** POSIX.1-2008 规定 `errno` 是 thread-local 的宏展开
（`*__errno_location()` 一类），每个线程各有一份。工作线程里发生的 `ENOENT`
不会出现在主线程的 `errno` 里；主线程读到的是自己上一次调用留下的残留值。
所以任务函数在返回前把 `errno` 存进槽位，主线程只用 `strerror(task->saved_errno)`。

**跨线程读槽位为什么不需要额外同步。** 工作线程执行完任务函数后，
要在持有池内部互斥量的状态下把 `running` 计数减一并 `broadcast`；
主线程的 `threadpool_wait` 在同一个互斥量上等待 `running == 0`。
这条"解锁 → 加锁"的链路构成 happens-before 关系，因此 `wait` 返回之后，
主线程看到的槽位内容一定是任务写完的。这不是巧合，而是用互斥量做屏障的必然结果——
先 `wait` 再读，顺序不能颠倒。

**只有 `-j 1` 与"只剩一个任务"两种退化。** `-j 1` 直接走顺序路径：一个工作线程的
"并行"只是多一次入队出队，还要为每个文件多写一个区间任务。任务总数为 1 时不建池，
把同一个 `task_exec` 内联执行——建池 + 一次 `wait` + `destroy` 要几十微秒，
在别处跑没有任何收益，而内联与提交走的是同一个函数，两条路的结果不会分叉。

**创建池失败直接报错，不静默退回串行。** 使用者写了 `-j 8` 就是期望并行，
悄悄改成单线程之后输出完全正常、只是耗时对不上，这种"能跑但不符合预期"的状态
比一条明确的错误信息难查得多。

**标准输入不并行。** 管道与终端不可 seek，只能顺序读一遍；`-j` 对无文件名的调用没有意义，
此时仍走顺序路径。

### 3.7 切分：切点必须落在分隔符上

把 `[0, size)` 切成若干段交给不同线程，唯一要保证的性质是：**每段的起点不是任何单词的
内部字节**。理由可以从状态机的计数规则直接推出来。

状态机只在 `OUT -> IN` 跳变时计一次词（3.1 节）。每段都从 `wc_counter_reset` 开始，
也就是以 `OUT` 状态起扫。若段起点 `p` 满足 `data[p]` 是分隔符（或 `p == 0`），那么：

- 任何词的首字节都不在 `p` 之前、又在 `p` 之后延续——因为 `p` 处是分隔符，词在 `p - 1`
  或更早就结束了；
- 因此该词已经在前一段被计过一次，而本段在 `p` 处的 `OUT` 状态不会把它再计一次；
- 本段内每个完整的词仍然在它的首字节处发生一次 `OUT -> IN`，各计一次。

反过来，若 `p` 落在词中间（`data[p]` 是字母数字、`data[p-1]` 也是），这个错就发生了：
前一段从词首起扫、计了一次；本段以 `OUT` 起扫、把词的后半截当成另一个词的开始，又计一次。
**行数与字节数完全正常**，只有词数偏大——所以这个缺陷不会被"数字看起来差不多"发现，
只能靠在多种切法下与整文件结果逐个比对（`tests/test_split.c` 的 226 项）。

**为什么往后对齐，而不是往前。** `wc_align_chunk` 从建议切点向后找第一个分隔符。
向前找（找上一个分隔符）也能得到合法切点，但要多读一段已经读过的数据，而且需要知道
"再往前是不是还有分隔符"，边界条件更绕。向后找只需要顺序读，且有一个有用的副产品：
**返回值对参数单调不减**——`from1 <= from2` 推出 `align(from1) <= align(from2)`。

**单调性省掉了边界夹紧。** 有了单调性，`bounds[k] >= bounds[k-1]` 恒成立，相邻段不会重叠，
内容不会被数两次。两个建议切点落进同一个超长单词时，两者都对齐到那个词的结尾，
中间那些段的长度为 0；空段不提交任务（一次分派约 600 ns，比空任务本身值钱）。
这条性质写进了 `tests/test_split.c` 的"单调性"用例，而不是靠驱动层再夹一次——
夹紧会把库违反性质的事实掩盖掉。

**一个 4 GB 的单词会怎样。** 对齐扫描找不到分隔符时会一直往后读，直到调用方传进去的
`limit`。若 `limit` 是文件末尾，那么每个建议切点都得把剩下的内容读完才肯放弃，
`ntasks` 最终只剩 1，驱动层退回顺序路径（见下一条）。结果正确，但代价按段数累加，
不是"多读一遍"——所以驱动层给对齐加了读取预算，见 3.8。

**段数怎么定。** 先按"每 MiB 一段"估，再压到 `jobs * 4` 以内，且文件小于 2 MiB 时
根本不切。两个理由：段数等于线程数时最慢的那段决定总时长（词长分布不均匀），
多切几段才能均衡；但段太小时，每段的切点对齐扫描与任务分派开始占可观比例。
8 MB 文件、`-j 8` 时实测 4.9× 加速（第 6.4 节），说明这个折中点在工作区间内。

**退化与回退都走同一条出口。** 不是普通文件（管道、目录、设备）、小于 2 MiB、
切出来只有一段，三种情况都返回 `SPLIT_SKIP`，由 `main` 转去顺序路径。为此
"顺序路径"必须始终是可用的，不能因为有了切分路径就把它当死代码删掉。

### 3.8 对齐扫描的读取预算

`wc_align_chunk` 只在两处停下：找到分隔符，或者到达调用方给的 `limit`。把 `limit`
传成文件末尾，这个"继续往后读"就没有上界：

- 正常文本里分隔符平均每 5~6 字节出现一次，一次对齐通常只读几个字节
  （8.2 MiB 文本、7 个建议切点，实测合计 **15 字节**）；
- 但整段内容落在同一个超长单词里时（基因序列、单行 minified JSON、日志里粘的一段
  base64），每个建议切点都要一路读到文件末尾才放弃。

代价按段数累加：第 k 个切点从 `k * size / nchunks` 读到 `size`，合计约
`(nchunks - 1) * size / 2`。`-j 16` 时 `nchunks = 64`，一个 64 MiB 的全字母文件因此
被读 **31.5 遍**，全部读完才得出"切不动"的结论，然后把顺序路径再走一遍。结果完全正确，
只是慢——这类退化不会让任何断言失败，只能靠可观测量发现（5.10）。

**做法：把 `limit` 换成"建议切点 + 预算"，预算是驱动层的策略，不是库的语义。**
所以 `wordcount.h` 与 `wordcount.c` 一行都没改：`wc_align_chunk` 本来就把
"`[from, limit)` 内没有分隔符"表达成 `*out == limit`，而 3.7 已经把这个返回值定义为
"这一段没有可用切点、并进上一段"。驱动层做的只是把 `limit` 从 `size` 换成
`min(size, suggested + budget)`，并把 `aligned == scan_to` 的切点丢掉。

**预算是 `min(段长 / 4, 1 MiB)`，不是固定的 1 MiB。** 第五轮的预算是一个固定字节数，
它只把"31.5 遍"压到"1 遍"，而 1 遍在两个地方仍然太贵：

- 对齐读取发生在 `nchunks - 1` 个切点上，总量随段数线性增长，段数又随 `-j` 线性增长。
  64 MiB 文件、`-j 16` 时 63 个切点各读 1 MiB，合计 63 MiB，是文件大小的 98%
  （6.5 的实测），而这些字节之后还要被计数再读一遍——等于多读近一倍。
- 反过来，段数少的时候（`-j 2`、`-j 4`）这个固定的 1 MiB 又显得浪费：段长 8 MiB 时
  只在切点附近找分隔符，读 1 MiB 与读 256 KiB 的命中率没有区别。

把预算与段长挂钩，总量就有一条与 `-j`、与段数都无关的上界：

    Σ budget_i ≤ Σ chunk_i / 4 = size / 4

这个不等式只用到 `min(x, ALIGN_SCAN_BYTES) ≤ x` 一条，既不依赖段长是否均匀，也不依赖
有多少个切点被放弃（放弃只会减少读取）。**最坏情况下对齐读取是文件的 25%**，
配合计数本身的一遍，总 I/O 量是文件大小的 1.25 倍；第五轮的固定预算在同一个输入上是
1.98 倍（6.5 节的两组数据）。

**为什么除数取 4。** 对齐读取是纯附加 I/O：读过的字节随后还要被计数再读一遍，它直接
抬高总 I/O 量，所以它是纯损耗。除数越小越省 I/O，但丢切点的概率越高——分隔符稀疏的
正常输入（行很长的日志、CSV）会因此损失并行度。1/4 是最坏情况附加 I/O 达到文件大小
25% 的那个点：64 MiB 全字母文件、`-j 16` 时实测 24%、耗时 169 ms，顺序路径 154 ms，
而固定 1 MiB 预算的同一输入是 98%、213 ms（6.5）。

**这个 4 现在有实测支撑了（6.6）。** 判据是"预算 / 被接受切点的最长扫描"，也就是预算
比这个文件的切点真正需要的距离宽松多少倍：

| 输入 | 行内最坏距离 | 最紧一档（`-j 8/16`）的预算 | 余量 |
|---|---|---|---|
| 行 4 KiB 的长行 CSV | 4 095 | 256 KiB | 64× |
| 行 64 KiB 的单列大字段 | 65 535 | 256 KiB | 4× |
| 行 1 MiB 的极端形态 | — | 256 KiB | 全部切点被放弃 |

也就是说，这套参数的覆盖边界落在"行长 ≈ 预算"这个位置：实测 256 KiB。现实里长行
CSV 与日志的行长多在几 KiB 到几十 KiB，最紧的那一类还留着 4 倍余量。

**为什么没有改成 1/8。** 改小除数换来的是最坏浪费从 25% 降到 12.5%——在 16 MiB 的
极端输入上就是从 3.9 MB 降到约 2 MB，十几毫秒（6.6 的耗时列）；代价是把可切的行长
上限从 256 KiB 砍到 128 KiB，也就是"本来能并行的文件退化成顺序"。一边是十几毫秒的
损耗，另一边是可能整个文件退回单线程，这两者不是一个量级。反过来，改成 1/16 会让
96 KiB 行的切点开始被放弃，`check_align_budget.sh` 第四类输入会直接失败——那条断言
就是给这个方向划的下界。

**1 MiB 这个上限仍然保留。** 它管的是相反的方向：段本来就很大时（低 `-j` + 大文件），
比例预算会跟着段长一起膨胀。400 MiB 文件、`-j 8` 时段长 12.5 MiB，比例预算会是
3.1 MiB，而这个文件读 1 MiB 早就找到分隔符了。两个量各管一头：
比例负责"总量封顶"，上限负责"单次不会过分"。

**为什么丢切点而不是夹紧。** 夹紧到上一个边界会产生零长度段：无害，却把"库返回了
limit"这个事实抹掉。这与 3.7 拒绝夹紧是同一个理由——能让错误暴露的地方，不要就地修正。

**丢切点为什么仍然正确。** 预算只截短搜索区间，不改搜索起点：找到了，返回的一定是
"≥ 建议切点的第一个分隔符"，所以被接受的边界序列仍然单调不减（3.7 的单调性论证不受
影响）；被跳过的那一段由前后两个被接受的边界夹住，内容照旧统计、且只统计一次。
`tests/test_split.c` 里 3 MiB 文件嵌 1 MiB 单词的用例，专门让三个建议切点落在
"接受 / 放弃 / 接受"的顺序上，把这条钉住。

## 4 构建

```bash
make            # 构建静态库 bin/libwordcount.a 与命令行工具 bin/wordcount
make lib        # 只构建静态库
make cli        # 只构建命令行工具
make test       # 构建并运行两个测试程序（test_wordcount + test_split）
make check      # 与 wc 交叉验证 + 并行/顺序一致性 + 切分一致性 + 对齐预算 + 混合负载调度
make sanitize   # 用 ASan + UBSan 重新构建并跑测试，产物在 bin/sanitize/
make tsan       # 用 TSan 重新构建并跑测试，产物在 bin/tsan/
make bench      # 缓冲区大小、并行度、对齐预算、混合负载的吞吐测量
make clean      # 删除 bin/（含全部变体）
```

变体构建使用独立输出目录，是因为 make 判断是否重建只比较时间戳、不比较编译选项：
共用 `bin/` 时先跑 `make sanitize` 再跑 `make`，普通构建会认为目标已是最新，
留下一个插桩过的可执行文件。

链接 `bin/wordcount` 时除了 `libwordcount.a`，还要链接一份 thread-pool 的静态库。
它不由使用者从 `../thread-pool/bin/` 里取，而是由本模块的 Makefile 现场建到
`bin/thread-pool/` 下：

```make
POOLDIR  := ../thread-pool
POOLOUT  := $(OUT)/thread-pool
POOLLIB  := $(POOLOUT)/libthreadpool.a

$(POOLLIB):
	@$(MAKE) --no-print-directory -C $(POOLDIR) lib \
		OUT=$(abspath $(POOLOUT)) CFLAGS='$(CFLAGS)'
```

三个理由：`make -C src/word-count` 从干净工作树就能构建，不必先去 thread-pool 里
`make` 一次；`sanitize` / `tsan` 变体拿到的是**同样插桩过**的池，否则"测试跑过了，
但池里发生的错误从没被 ASan 检查过"；`make clean` 一次能清干净本模块的全部产物。
代价是根 `make` 会把 thread-pool 编译两遍（各自一份 `bin/`），编译它只要几百毫秒。

`OUT` 传给子 make 时必须转成绝对路径：子 make 的工作目录是 `$(POOLDIR)`，
相对路径会落到 `../thread-pool/` 之下而不是本模块的输出目录里。

默认编译参数：

```make
CFLAGS   ?= -std=c11 -Wall -Wextra -Wconversion -O2 -g -pthread
CPPFLAGS += -Iinclude -I$(POOLINC) -D_POSIX_C_SOURCE=200809L
```

| 参数 | 作用 |
|---|---|
| `-std=c11` | 固定语言标准，避免依赖编译器的默认方言 |
| `-Wall -Wextra` | 常规警告集 |
| `-Wconversion` | 检查隐式窄化转换。本主题最关键的一处缺陷只有它能发现（见第 7 节） |
| `-O2` | 优化；模块不依赖任何未定义行为，优化不会改变结果 |
| `-g` | 保留调试信息，配合 `make sanitize` 时能定位到具体行 |
| `-pthread` | 驱动层链接线程池需要；库本身不引用 pthread，但编译选项全模块共用 |
| `-D_POSIX_C_SOURCE=200809L` | `-std=c11` 会定义 `__STRICT_ANSI__`，关掉 glibc 的默认扩展，`getopt` 的声明就看不到了；不定义它时 `getopt` 退化成隐式声明 |

`CFLAGS ?=` 用的是条件赋值，因此可以在命令行上覆盖，例如
`make CFLAGS="-std=c11 -Wall -Wextra -Wconversion -O0 -g -funsigned-char"`
用来模拟 `char` 无符号的平台。

**把模块作为库使用：**

```bash
cc -std=c11 -Wall -Wextra -Wconversion -O2 -Iinclude your_app.c bin/libwordcount.a -o your_app
```

只需要 `-Iinclude` 指向头文件，`libwordcount.a` 指向静态库。链接顺序上库要放在
引用它的目标文件之后——`ar` 生成的静态库按需抽取成员，顺序反了会报未定义符号。

不需要 `-pthread`，也不需要 thread-pool 的头文件与库：线程池只被本模块的驱动层
（`src/main.c`）使用，`libwordcount.a` 对它是零引用。这条性质不是靠约定维持的，
而是每次构建 `bin/wordcount` 之外还会单独链接 `libwordcount.a` 验证出来的。

### 5.3 交叉验证

`make check` 用与模块完全无关的路径独立算一遍，逐项比对：

```
与 wc / 独立方法交叉验证

          行          词         字节  文件
---------------------------------------------------------------
           2           14            118  testdata/a.txt
        1762       114588         617637  testdata/b.txt

```

三个计数的验证方式不同：

- **行数、字节数**：直接与 GNU `wc` 比对。这两个量的定义没有歧义，应当完全一致。
- **单词数**：`wc -w` 的口径不同（按空白切分），不能直接比。改用等价变换
  `tr -c '[:alnum:]' '\n' | grep -c '[[:alnum:]]'`——把所有非字母数字的字节换成换行，
  再数非空行数，即"最长连续字母数字段"的个数。这条命令与模块的实现没有任何共享代码，
  是真正独立的第二条路径。

脚本里固定了 `LC_ALL=C`，保证 `tr` 与 `grep` 的字符类按字节处理，不受调用环境的区域设置影响。
不加这一句，脚本在不同机器上的行为会不一致。

### 5.5 端到端

| 场景 | 命令 | 结果 |
|---|---|---|
| 标准输入 | `printf "hello world\nfoo\n" \| ./bin/wordcount` | `2 3 16`，退出码 0 |
| 单文件 | `./bin/wordcount testdata/a.txt` | 行 2、词 14、字节 118 |
| 多文件 | `./bin/wordcount testdata/a.txt testdata/b.txt` | 逐行输出，末尾补 `total` 行 |
| 并行多文件 | `./bin/wordcount -j 4 testdata/a.txt testdata/b.txt testdata/a.txt` | 输出与不带 `-j` 时逐字节相同 |
| 单文件切分 | `./bin/wordcount -j 8 big.log` | 切成若干段并行统计，输出与不带 `-j` 时逐字节相同 |
| `-j` 越界 | `./bin/wordcount -j 0 testdata/a.txt` | 报错到 stderr，退出码 2 |
| 空输入 | `: \| ./bin/wordcount` | `0 0 0`，退出码 0 |
| 文件不存在 | `./bin/wordcount testdata/nonexistent.txt` | 报错到 stderr，退出码 1 |

退出码是关键：脚本里用 `if ./bin/wordcount "$f"; then` 或 `&&` 串联时，
只有退出码正确，失败才能被检测到。多个文件时只要有一个失败，最终退出码就是 1，
但其余文件仍然会被继续处理，不会因为第一个错误就中断整批任务。

### 5.6 内存与资源

| 验证项 | 结果 |
|---|---|
| ASan（越界、泄漏） | 无报告 |
| 并行路径的槽位数组与池对象 | ASan 退出检查无泄漏 |
| 文件描述符泄漏 | 连续 500 次 `wc_count_file`，`/proc/self/fd` 计数 6 → 6，**净增 0** |
| 非法参数（各接口传 NULL） | 全部返回 `WC_ERR_PARAM`，不崩溃 |
| `wc_counter_reset(NULL)` / `wc_counter_get(NULL, &st)` | 直接返回，不崩溃 |

文件描述符那一项值得单看：`ulimit -n` 是 1024，如果每次调用泄漏一个描述符，
同一个进程里累积约 1020 次就会让 `fopen` 因 `EMFILE` 失败。一次性程序看不出这个问题——
`main` 调用完就退出，进程结束时内核统一回收；但只要把它放进长期运行的循环，
泄漏立刻变成硬故障。这也是"资源所有权必须跟着作用域走"最实际的理由。

### 5.7 并行与顺序的一致性

`make check` 的第二段运行 `tests/check_parallel.sh`：构造 6 个长度递增的文件
（118 B ~ 3.1 MB），先把顺序模式的输出存成基线，再用 `-j 1/2/3/4/8/16` 各跑一遍，
逐字节比对 **stdout、stderr、退出码**三个产物。

文件长度递增是有意的：短任务先完成、长任务后完成，完成顺序与 argv 顺序必然不同。
如果输出顺序跟着完成顺序走，这里立刻就会 diff 出差异。

```
并行与顺序的输出一致性
---------------------------------------------------------------
  顺序基线：6 个文件（118 B ~ 3.1 MB），输出 7 行（含 total）
  stdout / stderr / 退出码  一致    -j 1
  stdout / stderr / 退出码  一致    -j 2
  stdout / stderr / 退出码  一致    -j 3
  stdout / stderr / 退出码  一致    -j 4
  stdout / stderr / 退出码  一致    -j 8
  stdout / stderr / 退出码  一致    -j 16
  stdout / stderr / 退出码  一致    -j 8 单文件
  stdout / stderr / 退出码  一致    -j 4 含不存在的文件
  stdout / stderr / 退出码  一致    -j 2 全部不存在
  退出码 2，有错误提示            -j 0 / -j abc 被拒绝

```

只比 stdout 是不够的。并行版本最容易丢的两件事恰好不在 stdout 里：
错误信息落到 stderr 的**次序**，以及"有一个文件失败时退出码是否仍是 1"。
三组边界用例各自盯着一个方向：

| 用例 | 盯的是什么 |
|---|---|
| `-j 8` + 单文件（236 KB） | 小于 2 MiB 不切分，必须退回顺序路径，连"没有 total 行"都一样 |
| `-j 4` + 中间夹一个不存在的文件 | 错误必须落在 argv 顺序的那一位，同批其它文件的结果不能消失 |
| `-j 2` + 全部不存在 | `total` 行不该出现，退出码必须非 0 |

最后一项验证参数校验：`-j 0` 与 `-j abc` 都要以退出码 2 结束并给出提示。

### 5.9 单文件切分与顺序的一致性

`make check` 的第三段运行 `tests/check_split.sh`（87 项比对）。它比第二段多做了一件事：
**先证明切分真的发生了**。

原因是这条断言有个陷阱——"切分输出 = 顺序输出"在切分根本没有发生时也成立。
文件小于 2 MiB、不是普通文件、所有切点被同一个词吃掉，这三种情况都会退回顺序路径，
那时输出当然一样。测试如果只比输出，就在什么都没测到的情况下报绿。所以脚本先设
`WORDCOUNT_TRACE_SPLIT=1` 让驱动把"切成了几段"打到 stderr，断言段数 **≥ 2**，
再关掉它做逐字节比对。

这个开关只在环境变量存在时生效。不加命令行选项是刻意的：正常调用下三种方式的
stdout 与 stderr 必须完全一致，多一个 `-v` 就会破坏这条契约。

五类输入各跑 `-j 2/3/4/8/16`：

| 输入 | 大小 | 盯着什么 |
|---|---|---|
| 混合文本（a.txt + 6 份 b.txt） | 3.7 MB | 正常路径，切出 3 段 |
| 截断到 2 500 000 字节（无结尾换行） | 2.5 MB | 文件末尾没有分隔符、且长度落在词中间 |
| 全是一个字符 `a` | 3 MiB | 没有可用切点，只应切出 1 段并退回顺序路径 |
| 全是空格 | 3 MiB | 每个字节都是分隔符，切点密集，0 词 0 行 |
| 截到 1 MiB | 1 MiB | 低于门槛，不该切分 |

另外两条独立断言：`-j 4` 输出的字节数必须等于 `wc -c` 给出的文件大小（不依赖另一条
代码路径）；目录参数（`testdata`）在两条路径下的错误信息必须逐字节相同——`open` 对目录
是成功的，是 `fstat` 的 `S_ISREG` 判断把它挡回顺序路径，最后由 `fread` 报 `EISDIR`。

```

---------------------------------------------------------------

  stdout / stderr / 退出码  一致    目录参数 · -j 4

```

**反向验证**（把正确实现改坏，确认测试抓得住）三处，都在 Ubuntu 上实跑：

| 注入 | 结果 |
|---|---|
| 驱动层不做切点对齐，直接用平均分出来的偏移 | `check_split.sh` 3 组不一致（词数偏大） |
| `wc_align_chunk` 在找不到分隔符时返回 `from` 而不是 `limit` | `check_split.sh` 6 组不一致（`oneword` 的 5 种 `-j` 全中） |
| `wc_count_fd_range` 把"提前遇到 EOF"当成正常结束 | `test_split` 2 项失败：`状态码 0，期望 3`、`截短时 out 未被修改 实际 (行 0, 词 1, 字节 4)` |

### 5.10 对齐读取预算

`make check` 的第四段运行 `tests/check_align_budget.sh`（72 项比对）。它验证的是
3.8 那条策略，判据全部来自 `WORDCOUNT_TRACE_SPLIT` 打出的六个数：段数、建议切点个数、
被放弃的个数、对齐扫描读掉的字节数、每个切点的预算、被接受切点的最长扫描。

为什么不能用"输出与顺序一致"当判据：加不加预算，输出**逐字节相同**。测试如果只比输出，
把预算整个删掉也照样报绿。这是 5.9 那个陷阱的另一种形态——上一轮是"切分没发生也成立"，
这一轮是"预算没生效也成立"。同一个道理：**先问这条断言在功能没生效时会不会也通过**。

四类输入，四种期望：

| 输入 | 大小 | 期望（`-j 4`） |
|---|---|---|
| 全是字母 `a` | 32 MiB | 15 个建议切点全部放弃，段数退化为 1 |
| 1 MiB 文本 + 4 MiB 单词 + 1 MiB 文本 | 6 MiB | 只放弃单词内的 4 个切点，仍切出 2 段 |
| 正常文本（14 份 `b.txt`） | 8.2 MiB | 一个切点都不放弃 |
| 每行 96 KiB、行内无空白 | 8 MiB | 一个切点都不放弃，最长扫描在行长量级 |

前三类分别对应"极端稀疏""部分稀疏""密集"，第四类是第七轮补的：前两类都测不出
"预算刚好够用"这一档，而 3.8 的除数正是在这一档上被约束的。

四类输入各跑 `-j 2/4/8/16`，每次都做两件事：与顺序输出逐字节比对，以及核对下面四条
不变量。边界条件用 `-j 4` 断言一次——段数与放弃个数是文件内容与 `-j` 的联合函数，
拿每个 `-j` 都断言等于把用例绑死在某个段数上。

**不变量一：预算公式。** 段数 `nchunks = 建议切点 + 1`，段长 `size / nchunks`，
期望预算 `min(段长 / 4, CAP)`，与 `TRACE` 报的数逐字节相等（`CAP` 与 `ALIGN_SCAN_BYTES`
同值、除数与 `ALIGN_BUDGET_DIV` 同值，改常量必须同步改脚本）。

**不变量二：`Σ 读取 ≤ size / 4`。** 与 `-j` 无关。正常文本的对齐读取量另有一条更紧的
上限 `≤ 64 KiB`，用来发现"对齐改成逐块读整个区间"之类的退化。

**不变量三：被接受切点的最长扫描严格小于预算。** 第七轮新增。它防的是一种写法上的
退化：如果把被放弃的那次扫描（必然读满预算）也算进最大值，这个量就恒等于预算，
变成预算的副本——而它存在的意义正是"这个文件的切点离分隔符最远有多远"。前两条
不变量对这种写法全绿，因为它们只看总量与公式。

**不变量四：稀疏分隔符的文件一个切点都不该放弃。** 也是第七轮新增，给除数划下界。
它单独配一条"输入确实稀疏"的断言（最长扫描 `>= 16384`），否则把输入造成密集分隔符
文本也能通过——那时测的根本不是这件事。

四条断言分工明确：**公式那条只证明"算对了"，读取量那条才证明"用上了"，
最长扫描那条证明"量的是真东西"，稀疏那条证明"余量还是正的"**。注入验证里能看到
前两条不是一回事（下面第二条注入）。

再一条兜量级回归的：32 MiB 全字母文件的 `-j 4` 不得比顺序慢 3 倍。

实测（CI / ubuntu-22.04 / gcc 11.4.0，脚本每次运行现造输入；全部 72 项通过）：

```
  oneword · 全部切点被放弃               正确    15 个建议切点全部放弃，退化为 1 段
  longword · 只放弃超长词内的切点     正确    5 个建议切点放弃 4 个，仍切出 2 段
  mixed · 正常文本不放弃切点           正确    7 个建议切点全部接受，8 段
  sparse · 稀疏分隔符不放弃切点       正确    7 个建议切点全部接受，8 段，最长扫描 98303 字节
  sparse · 输入确实是稀疏分隔符       正确    最长扫描 98303 字节（行 96 KiB）
```

**反向验证四条**（都在临时副本上改常量或改一行，改完重编，推上 CI 跑；不是本地推测）。
四条各打一个方向，合起来说明四条不变量不是重复的。

第一条：把 `ALIGN_BUDGET_DIV` 改成 1，即"预算 = 段长，再被 1 MiB 封顶"——这正是第五轮
那个固定 1 MiB 的行为。**22 项失败**（第六轮同类注入在 41 项版本上是 18 项，那时只有
三类输入）：

```
  oneword · -j 4 预算应为 524288：TRACE 报 1048576，段长 2097152，size 33554432
  oneword · -j 4 对齐读取超出 size/4：15728640 字节 > 8388608（文件的 46%）
  oneword · -j 8 对齐读取超出 size/4：32505856 字节 > 8388608（文件的 96%）
  oneword · -j 16 对齐读取超出 size/4：32505856 字节 > 8388608（文件的 96%）
  longword · -j 2 预算应为 262144：TRACE 报 1048576，段长 1048576，size 6291456
  mixed · -j 2 预算应为 270216：TRACE 报 1048576，段长 1080864，size 8646918
```

三处细节值得记：

- `oneword · -j 2` 的两条断言在注入版里**照样通过**。`-j 2` 时段长 4 MiB，
  比例预算算出来是 1 MiB，与固定预算取值相同——两种策略在这个点上本来就没有分歧。
  能区分它们的只有 `-j ≥ 4`。这也说明"多跑几个 `-j`"不是凑数，是为了覆盖策略分歧点。
- `mixed` 只失败公式那条，读取量那条照样通过（正常文本只读 6 字节，离上界差六个数量级）。
  所以**只看读取量的测试会漏掉"公式算错但恰好没读超"的实现**，两条断言必须都在。
- **最长扫描那条在这条注入下全绿**：预算改成 1 MiB 只会让被接受的扫描更小，
  报出来是 0 字节或 8 字节。这说明它管的是相反的方向（"这个数字还是不是它声称的量"），
  不重复公式与总量两条——第四条注入会把它单独打出来。

第二条：把 `limit` 改回文件末尾（`scan_to = size`），预算算了但不用。**14 项失败**：

```
  oneword · -j 2 对齐读取超出 size/4：117440512 字节 > 8388608（文件的 350%）
  oneword · -j 4 对齐读取超出 size/4：251658240 字节 > 8388608（文件的 750%）
  oneword · -j 8 对齐读取超出 size/4：520093696 字节 > 8388608（文件的 1550%）
  longword · -j 2 对齐读取超出 size/4：10485800 字节 > 1572864（文件的 166%）
  longword · -j 2 最长扫描 4194312 字节：应当小于预算 262144（说明把被放弃的扫描也算进去了）
```

公式那条 12 项全过：`TRACE` 仍然把 `align_budget` 算对并打印出来，只是没有被拿去做
`limit`。败的 8 项读取量全是 `oneword` 与 `longword`；`mixed` 与 `sparse` 那 8 项照样
通过——分隔符密的输入即使不设预算也只能读几个字节。这就是"算对了"与"用上了"的分界，
也是为什么不能只留公式断言。`251658240` 字节 = 240 MiB，正是 32 MiB 文件 `-j 4`
（16 段）在无预算下的 `size × (nchunks - 1) / 2` 推算值。

这里还多出一类失败：`longword` 的最长扫描断言。预算不生效时，一个被接受的切点可能
跨过 4 MiB 的长词才找到分隔符，扫描距离 4 194 312 字节——这正是不变量三要抓的形态，
只是这条注入同时踩了两个问题。

第三条：把"被放弃的那次扫描"也算进最长扫描（把更新语句挪到 `continue` 之前）。
**8 项失败**，全部是 `oneword` 与 `longword` 的最长扫描断言，公式与总量一条都没败，
`mixed` 与 `sparse` 也全过（它们没有切点被放弃）：

```
  oneword · -j 2 最长扫描 1048576 字节：应当小于预算 1048576（说明把被放弃的扫描也算进去了）
  oneword · -j 4 最长扫描 524288 字节：应当小于预算 524288（说明把被放弃的扫描也算进去了）
  longword · -j 4 最长扫描 262144 字节：应当小于预算 262144（说明把被放弃的扫描也算进去了）
```

这条注入就是"不变量三"存在的理由：**改坏之后功能与输出完全不变，只有这个数变了**。
前两条不变量对它全绿，`rd ≤ size/4` 也全绿。

第四条：把除数改成 16（实现与脚本同时改，模拟"真的把除数调小"）。**1 项失败**：

```
  sparse · 稀疏分隔符不该放弃切点：段数 6，建议切点 7，放弃 2，最长扫描 65535
```

预算从 256 KiB 降到 64 KiB，7 个建议切点里那两个"距行尾 98 304 字节"的被放弃，
段数从 8 降到 6，其余不变量都还成立（读取量反而降到 4%）。只败这 1 项是因为它只在
`-j 4` 上断一次，这也正好说明它与前三条的分工：它是一条**下界**（"除数不能再小"），
不是性能断言——除数调小时除了丢切点，别处看不出任何异常。

### 5.11 多文件与切分共用一条队列

`make check` 的第五段运行 `tests/check_mix.sh`（24 项比对）。第八轮之前，`-j` 的两条
路径各有一份测试（5.7 的 `check_parallel.sh` 覆盖"多个小文件"、5.9 的 `check_split.sh`
覆盖"单个大文件"），而"多个文件、其中几个大到该切"这个组合没有走过——它恰是现在
唯一的一条路径。

判据分两类。

**一类是逐字节比对。** 4 个文件的混合集（118 B / 617 KB / 3 MiB / 16 MiB）跑
`-j 2/3/4/8`，与顺序输出的 stdout / stderr / 退出码逐字节比对；再加两条"不存在的文件
排在中间"的比对，错误必须落在 argv 顺序上的那个位置，且不能让同批其它文件的结果消失。

**一类是调度可观测量。** 四条断言，全部读 `WORDCOUNT_TRACE_SPLIT`，`-j 2` 下的期望值：

| 断言 | 期望 | 功能没生效时 |
|---|---|---|
| 切分记录条数 = 不小于 2 MiB 的文件数 | 2 条，每条的段数 ≥ 2 | 一个文件一个任务时 0 条，而输出照样一致 |
| 任务数 = 各文件段数之和 + 整文件任务数 | 13 = 11 + 2 | 退化成 4 = 0 + 4 |
| 工作线程数 | = `min(-j, 任务数)` | 直接取 `-j` 时，任务数不足的输入会多建线程 |
| 首个任务的字节数 | ≥ 2 MiB（16 MiB / 8 段） | 按 argv 顺序提交时是 118 字节 |

第二类是重点。前两类断言（逐字节比对、切分记录条数）在"每个文件都退化成一个整文件
任务"时**行为不同**：逐字节全绿、切分记录一条都没有——所以只要不把"切了没有"变成
可观测量，任何实现都能通过。这与 5.9、5.10 记的两个假通过是同一条原则。

第四条断言的构造值得单独说。**最大的文件必须放在 argv 末尾**：若它排在最前，
"按 argv 顺序提交"与"按长度降序提交"给的首个任务都是它，这条断言就区分不了两种写法。
放在最后之后，两种写法的首个任务分别是 118 字节与 2 MiB，差四个数量级。
`-j 2` 时 16 MiB 文件切 8 段、每段 2 MiB，其余任务的权重都不超过 1.5 MiB，
所以阈值取 2 MiB 是"最大那段的段长"，不是随手挑的整数。

24 项由三部分组成：**6 组三元比对**（4 个 `-j` + 2 条错误路径，每组比 stdout / stderr /
退出码）、**12 条逐 `-j` 的调度断言**（4 个 `-j` × 3 条）、**6 条单点断言**（LPT、
小于 2 MiB 不切分、单文件任务数 = 段数、`total` 行的字节数、stdout 行数、
`total` = 四个文件各自结果之和）。6 + 12 + 6 = 24，与脚本最后打印的项数一致。

**反向验证两条**（都在临时分支上改一行，推 CI 跑）：

| 注入 | 失败项数 | 抓到它的断言 |
|---|---|---|
| LPT 的排序方向写反（最短的先提交） | **1** | 只有"首个任务 ≥ 2 MiB"，实测报 `首个任务 118 字节` |
| 多文件时不切分（恢复"只有单个文件才切"的老行为） | **9** | 切分记录条数 ×4、任务数 ×4、工作线程数 ×1 |

两条的失败集合**不相交**，这是它们都必须存在的原因：第二条注入下每个文件都退化成一个
整文件任务，`16 MiB` 那个仍是最大的任务，所以"首个任务 ≥ 2 MiB"照样通过；反过来
第一条注入下切分照常发生，只有首个任务的字节数变了。一个断言管"切了没有"，
另一个管"排序对不对"，缺一条就会漏掉对方那一半。

第二条的失败输出里还能看到 `共 4 个任务（其中整文件任务 4 个）`——调度行本身就是
诊断信息：不看它，只知道"输出一致"。

第一条最初的做法是**直接删掉 `qsort`**，结果 CI 在第一步（零警告构建）就以
`-Wunused-function` 失败——测试根本没跑到。这件事本身值得记：**"CI 失败"不等于
"测试抓到了"**，必须看失败发生在哪一步；改坏的代码如果连编译都过不去，
它对测试的检验力是零。改成"方向写反"之后编译无警告，失败才落在断言上。

## 6 性能

测试数据：`testdata/b.txt` 拼接 20 份，共 **12 352 740 字节**（11.78 MiB）、35 240 行、
2 291 760 词。各跑 20 轮取总时间，`-O2` 编译。

机器：AMD Ryzen 7 5700X（8 核 16 线程）/ Linux 6.8 / gcc 11.4.0。
第 6.3 节的并行度数据同样在这台机器上测。

### 6.1 与单文件实现、GNU `wc` 的对比

| 实现 | 20 轮总耗时 | 单轮 | 吞吐 |
|---|---|---|---|
| 单文件完善版（`fgetc` 逐字符扫描，提交 `cdb73f0`） | 1517 ~ 1537 ms | ~76 ms | ~162 MB/s |
| 本模块（`fread`，16 KiB 块） | 531 ~ 538 ms | ~27 ms | ~465 MB/s |
| `LC_ALL=C wc -l -w -c`（参考） | 1534 ~ 1545 ms | ~77 ms | ~161 MB/s |

**按块读取带来约 2.9 倍提升。** 差距全部来自 I/O 方式：`fgetc` 每次调用都要进入 stdio 内部
逻辑（检查缓冲区、必要时加锁），对每个字节都走一遍；`fread` 一次把 16 KiB 搬进用户缓冲区，
之后是纯内存的顺序扫描。

顺带说明为什么模块比 `wc` 快：GNU `wc` 的 `-w` 用的是逐字节的状态判断加 `iswspace`
一类的多字节处理路径，在 C locale 下反而更重。这不代表本模块"比 `wc` 好"——
`wc` 要处理的是任意区域设置下的多字节字符，代价花在了本模块明确不支持的场景上。

把 `wc` 的三个统计分开测，可以确认瓶颈在哪里：

| 命令 | 20 轮总耗时 | 单轮 |
|---|---|---|
| `wc -c` | 15 ms | ~0.8 ms |
| `wc -l` | 53 ms | ~2.7 ms |
| `wc -w` | 1578 ms | ~79 ms |
| `wc -l -w -c` | 1534 ms | ~77 ms |

字节数和行数几乎是纯内存带宽（`-c` 甚至可以用 `fstat` 拿到大小，不需要读内容），
耗时完全在词数统计上。三个一起做和只做 `-w` 的时间基本相同，说明**一遍扫描的时间由最重的那一步决定**，
多统计几项几乎不增加成本——这也是本模块把三个计数放在同一次扫描里完成的原因。

### 6.2 缓冲区大小的取舍

同一输入，20 轮，重复测三次：

| 块大小 | 第一次 | 第二次 | 第三次 | 均值 |
|---|---|---|---|---|
| 256 B | 577 ms | 565 ms | 564 ms | 569 ms |
| 1 KiB | 562 ms | 555 ms | 558 ms | 558 ms |
| 4 KiB | 558 ms | 547 ms | 552 ms | 552 ms |
| 16 KiB | 515 ms | 534 ms | 531 ms | 527 ms |
| 64 KiB | 517 ms | 537 ms | 531 ms | 528 ms |

结论：

1. **256 B 到 16 KiB 只差约 8%**，说明块大小只要不极端偏小，就对吞吐影响有限。
2. **超过 4 KiB 收益就很小。** 4 KiB 是常见文件系统的页大小，也是 stdio 默认缓冲区量级的取值。
3. **16 KiB 与 64 KiB 基本持平**，但 64 KiB 的栈占用是 16 KiB 的四倍。`wc_count_stream`
   把缓冲区放在栈上（不是 `malloc`），因此在栈空间受限的环境（线程栈默认往往只有几百 KB 到几 MB）
   上，64 KiB 是个不划算的赌注。

默认取 **16 KiB**，是在"吞吐已经不差"和"栈占用仍然安全"之间的折中。
需要更极端的取值时，通过 `-DWC_BUFFER_SIZE=n` 覆盖，不必改头文件。

顺带一个反面结论：模块早期版本试过 `getc_unlocked`，实测只快约 2%，落在测量噪声里。
它是 POSIX 扩展，去掉它等于去掉一个平台依赖，代价是那 2%——不值得。**先测量，再决定要不要换。**

### 6.3 并行度

输入：8 个文件，每个由 8 份 `b.txt` 拼成，合计 **39 528 768 字节**（37.7 MiB）。
输入全在页缓存里，因此测的是扫描 + 系统调用的成本，不含磁盘等待。
每个配置跑 5 轮取合计，`make bench` 连续跑三次：

| 配置 | 第一次 | 第二次 | 第三次 | 相对顺序 |
|---|---|---|---|---|
| 顺序（无 `-j`） | 379 ms | 378 ms | 378 ms | 1.00× |
| `-j 1` | 380 ms | 380 ms | 380 ms | 1.00× |
| `-j 2` | 194 ms | 195 ms | 194 ms | 1.95× |
| `-j 4` | 100 ms | 100 ms | 100 ms | 3.79× |
| `-j 8` | 68 ms | 70 ms | 66 ms | 5.4~5.7× |

换算成单轮与吞吐（顺序取 378/5 ≈ 75.6 ms，`-j 8` 取 66~70 ms）：

| 配置 | 单轮 | 吞吐 |
|---|---|---|
| 顺序 | ~75.6 ms | ~523 MB/s |
| `-j 2` | ~38.8 ms | ~1019 MB/s |
| `-j 4` | ~20.0 ms | ~1976 MB/s |
| `-j 8` | ~13.2~14.0 ms | ~2820~2990 MB/s |

几点值得记下来：

1. **`-j 1` 与顺序的差别在 1% 以内**（380 vs 378 ms）。多出来的是每轮建池与停机的开销：
   创建一个工作线程 + 一次 `threadpool_wait` + `destroy` 的 join。相对 39 MB 的扫描量
   可以忽略，但这也说明"并行一定更快"不成立——收益必须由工作量摊掉固定成本。
2. **加速比在 8 线程时是 5.4~5.7，不是 8。** 机器是 8 核 16 线程（Ryzen 7 5700X），
   `-j 8` 正好占满 8 个物理核。剩下的差额来自三处：主线程提交与汇总本身是串行的、
   文件长度不完全相等（`-j 8` 时最短的任务先结束，尾部有等待）、以及 8 条流同时读
   页缓存时共享内存带宽与预取器。
3. **小文件也有收益，但收益来源不同。** 500 个 118 字节的文件，各跑 20 轮：
   顺序 67 ms（每轮 3.35 ms）、`-j 4` 41 ms、`-j 8` 36 ms，约 1.6~1.9×。
   此时扫描量可以忽略，时间几乎全在 500 次 `open`/`read`/`close` 系统调用上——
   并行的是系统调用，不是计算。这也解释了为什么它远不到 5 倍：系统调用在
   内核侧仍有共享的目录项缓存与文件表锁。

上面三张表是**第八轮之前**的实测：那时多个文件按文件分发，每个 4.7 MiB 的文件是
一个任务。现在同一命令的行为变了（每个文件都会再切成 4 段、共 32 个任务），
绝对值因此不可直接对照。用同一份输入（39 528 768 字节、8 个文件，每配置 5 轮取合计）
在 CI 的 `ubuntu-22.04` 运行器上重跑：

| 配置 | 第一次 合计 / 单轮 | 第二次 合计 / 单轮 |
|---|---|---|
| 顺序 | 415 / 83.0 ms | 641 / 128.2 ms |
| `-j 1` | 413 / 82.6 ms | 641 / 128.2 ms |
| `-j 2` | 233 / 46.6 ms | 332 / 66.4 ms |
| `-j 4` | 138 / 27.6 ms | 236 / 47.2 ms |
| `-j 8` | 136 / 27.2 ms | 239 / 47.8 ms |

两点只在这份输出内部成立：**`-j 1` 与顺序的差别在 0.5% 以内**（与旧实现同一条结论）；
**`-j 4` 与 `-j 8` 只差 1~2%**，说明运行器的并行度在 4 线程附近就饱和了，线程数
超过它能提供的核数没有收益。两次运行同一份代码差了 **1.54 倍**（顺序 415 → 641 ms），
比 `-j` 之间的任何差异都大——所以这组数只能看同一次输出内部的比值，跨运行比绝对值
没有意义。第八轮改动在这组输入上看不出差别（8 个等大的文件按文件分发本来就均衡），
任务划分方式的变化见 6.7。

### 6.4 单文件切分

输入：一个 **401 464 050 字节**（382.9 MiB）的文件，由 650 份 `b.txt` 拼接而成，
先完整跑一遍把它读进页缓存，再连续测三轮。段数按 3.7 节的规则自动定
（`min(jobs × 4, size / 1 MiB)`，每段不小于 1 MiB）：`-j 2/4/8/16` 实际切成
**8 / 16 / 32 / 64 段**，每段 50 / 25 / 12.5 / 6.3 MB。

| 配置 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 相对顺序 |
|---|---|---|---|---|
| 顺序（无 `-j`） | 761 ms | 760 ms | 759 ms | 1.00× |
| `-j 2` | 381 ms | 382 ms | 380 ms | 2.00× |
| `-j 4` | 201 ms | 192 ms | 192 ms | 3.96× |
| `-j 8` | 116 ms | 110 ms | 113 ms | 6.7~6.9× |
| `-j 16` | 79 ms | 80 ms | 78 ms | 9.6× |

五次运行的 stdout 与顺序基线 `cmp` 全部相同（401 MB 的计数是
`1145300 / 74482200 / 401464050`，恰好是 `b.txt` 的 650 倍）。

`-j 16` 到 9.6× 超过物理核数（8），说明这条路径已经不是纯 CPU 受限：
单遍扫描 401 MB 只用 78 ms，等于 5.1 GB/s，接近这台机器的内存带宽。
和 6.3 的 2.8~3.0 GB/s 相比，切分版更快的原因是不用同时维持 8 条独立的文件流与
8 组 stdio 缓冲区——一个 fd、一份 16 KiB 栈缓冲区、若干次 `pread`。

**切分本身的开销：单核上测不出来。** 用 `taskset -c 0` 把进程钉在一个核上，
跑同一个 401 MB 文件：

| 配置（单核） | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| 顺序 `fread` | 764 ms | 762 ms | 761 ms |
| `-j 8`（8 段，但只有一个核） | 761 ms | 761 ms | 759 ms |

两者在 0.5% 以内，切分版甚至略快。也就是说：切点对齐扫描（每段只读几个字节就
找到分隔符）+ 逐段 `pread` + 任务分派，这些加起来在这台机器上小于测量噪声。
`-j 2` 的 2.00× 也印证了这一点——如果每段有可观的固定开销，只有两个线程时
摊不掉，比值会明显低于 2。

**小文件的转折点。** 8 029 281 字节（7.7 MiB）的文件跑 20 轮（实际切成 7 段，
`-j 8` 时是 7 个工作线程）：

| 配置 | 20 轮合计 | 单轮 |
|---|---|---|
| 顺序 | 316 ms | 15.8 ms |
| `-j 2` | 189 ms | 9.45 ms |
| `-j 4` | 105 ms | 5.25 ms |
| `-j 8` | 64 ms | 3.20 ms |

`-j 8` 是 4.9×，比大文件的 6.7× 低，差额是进程启动与建池的固定成本——
单轮只有 3.2 ms，几百微秒的固定开销就占几个百分点。这也是 2 MiB 门槛的来源：
低于这个值，`open` + 建池 + 对齐扫描加起来已经和扫描本身同量级。

### 6.5 对齐扫描的读取预算

输入：一个 **67 108 864 字节**（64 MiB）的文件，全部填 `a`——一个词贯穿全文，
5.10 节里说的那种"每个切点都要读到末尾才放弃"的输入。各跑 3 轮，取合计耗时；
对齐读取量取自 `WORDCOUNT_TRACE_SPLIT`，是确定值，不随运行波动。

环境：内网 Ubuntu / Ryzen 7 5700X（8 核 16 线程）/ gcc 11.4.0 / 输入在页缓存里。
"旧"是把 `ALIGN_BUDGET_DIV` 改成 1 后重编的同一份代码——预算 = 段长再被 1 MiB 封顶，
也就是第五轮那个固定 1 MiB 的行为。两个二进制同一台机器同一批输入交替跑，
所以耗时可以直接比。

| 配置 | 段数 | 建议切点 | 预算/切点 | 对齐读取（新） | 对齐读取（旧） | 耗时（新） | 耗时（旧） |
|---|---|---|---|---|---|---|---|
| 顺序 | — | — | — | 0 | 0 | 154 ms | 同左 |
| `-j 2` | 1 | 7 | 1 MiB | 7 340 032（10%） | 7 340 032（10%） | 160 ms | 162 ms |
| `-j 4` | 1 | 15 | 1 MiB | 15 728 640（23%） | 15 728 640（23%） | 168 ms | 168 ms |
| `-j 8` | 1 | 31 | 512 KiB | 16 252 928（24%） | 32 505 856（48%） | 168 ms | 183 ms |
| `-j 16` | 1 | 63 | 256 KiB | 16 515 072（24%） | 66 060 288（98%） | 169 ms | 213 ms |

`-j 2` 与 `-j 4` 两行新旧完全相同，这不是测量误差，是两种策略在段长足够大时取值相同
（`段长 / 4 ≥ 1 MiB`），1 MiB 封顶先起作用。**分歧从 `-j 8` 开始**：段长降到 2 MiB，
比例预算 512 KiB 小于封顶值。这也是 5.10 里"多跑几个 `-j`"的理由——只测 `-j 4` 的话，
把策略改回固定预算，这一节的数据一行都不会变。

另一条独立的分歧点在 32 MiB 输入上（`check_align_budget.sh` 用的那个尺寸）：同一台机器，
`-j 8` 旧 35 ms 新 28 ms、`-j 16` 旧 35~36 ms 新 28 ms，而顺序路径是 26 ms。
也就是说固定预算让 `-j 16` 比顺序**慢 35%**，比例预算把它拉回到只差 8%——读取量从
文件大小的 96% 降到 24%，剩下的 8% 是"切不动"之后仍要退回顺序路径的那一趟。

旧实现（`limit` 传文件末尾）在同一输入上的对齐读取量按 `size × (nchunks - 1) / 2` 累加：
`-j 2` 3.5 遍、`-j 4` 7.5 遍、`-j 8` 15.5 遍、`-j 16` 31.5 遍文件，即
**224 / 480 / 992 / 2 016 MiB**。这组数字是推算的，公式在"一个分隔符都没有"的输入上
是精确的（每个切点必然读到底）；实测的是 5.10 那个 32 MiB 的注入版本——`-j 4`
（16 段）读 **251 658 240** 字节 = 240 MiB，与公式给出的 `32 × 15 / 2` 完全一致。

**"24%" 是怎么来的，以及它为什么不能再往下压。** 比例预算的上界是 `size / 4`，
封顶值则在段长超过 4 MiB 时接管，两个量取小，所以"24%"是这套参数在这个输入上
自然落到的位置，不是某一行的特例。要它更小只能改 `ALIGN_BUDGET_DIV`，代价是分隔符
稀疏的正常输入更容易丢切点——而这组全字母输入恰恰是最不该拿来做取舍依据的，
它的 `-j` 永远是退化的（段数为 1、退回顺序路径）。真正的取舍要在"行很长的日志"
这类输入上看，那组数据在 6.6。

**为什么这组数据主要看读取量而不是耗时。** 读取量是确定值，耗时不是。全字母文件的
`-j` 永远是退化的，耗时差别只反映"多读了多少"，而这个量已经被直接测出来了：拿确定值
当判据比拿毫秒数当判据可靠，尤其 CI 的共享运行器上单次耗时能差 2 倍。耗时列放在这里
是为了说明"多读 4 倍"在页缓存里值多少毫秒（`-j 16` 那行 44 ms），不是为了排名。

### 6.6 稀疏分隔符输入上的预算余量

6.5 那组输入一个分隔符都没有，只能回答"预算省掉了多少浪费"。这一节回答相反的
问题：**预算够不够用，还剩多少余量**。判据是 3.8 里新增的那个可观测量——被接受
切点的最长扫描，也就是这个文件的切点离最近的换行最远有多少字节。

三类输入都由 `tests/bench_align_sparse.sh` 现造（`make bench` 的第四段），每行只有
末尾一个换行、行内没有空白：`a` 组成的定长行，等价于"每行一条 base64"的日志。
前两组的行长整除段长，于是每个建议切点都恰好落在行首，测到的就是行尾的距离，
也就是这一组的最坏距离——这是构造出来的，不是碰巧。第三组的行长取 1048571
（不整除的奇数），测的是"预算只够覆盖一部分切点"的中间形态。

环境：GitHub Actions 的 ubuntu-22.04 / gcc 11.4.0。读取量、段数、切点数都是确定值，
与机器无关；耗时是 3 轮合计，只作参考量级。

**行 4 KiB，67 108 864 字节**（长行 CSV、每行一条 base64 的访问日志）

| `-j` | 段 | 放弃 | 预算/切点 | 对齐读 | 占比 | 最长扫描 | 余量 |
|---|---|---|---|---|---|---|---|
| 2 | 8 | 0 | 1 MiB | 28 665 | 0.04% | 4 095 | 256× |
| 4 | 16 | 0 | 1 MiB | 61 425 | 0.09% | 4 095 | 256× |
| 8 | 32 | 0 | 512 KiB | 126 945 | 0.19% | 4 095 | 128× |
| 16 | 64 | 0 | 256 KiB | 257 985 | 0.38% | 4 095 | 64× |

**行 64 KiB，33 554 432 字节**（单列大字段的导出文件）

| `-j` | 段 | 放弃 | 预算/切点 | 对齐读 | 占比 | 最长扫描 | 余量 |
|---|---|---|---|---|---|---|---|
| 2 | 8 | 0 | 1 MiB | 458 745 | 1.4% | 65 535 | 16× |
| 4 | 16 | 0 | 512 KiB | 983 025 | 2.9% | 65 535 | 8× |
| 8 | 32 | 0 | 256 KiB | 2 031 585 | 6.1% | 65 535 | 4× |
| 16 | 32 | 0 | 256 KiB | 2 031 585 | 6.1% | 65 535 | 4× |

**行 1 MiB，16 777 216 字节**（极端形态，行长超过预算）

| `-j` | 段 | 放弃 | 预算/切点 | 对齐读 | 占比 | 最长扫描 | 余量 |
|---|---|---|---|---|---|---|---|
| 2 | 1 | 7 / 7 | 512 KiB | 3 670 016 | 21.9% | 0 | — |
| 4 | 1 | 15 / 15 | 256 KiB | 3 932 160 | 23.4% | 0 | — |
| 8 | 1 | 15 / 15 | 256 KiB | 3 932 160 | 23.4% | 0 | — |
| 16 | 1 | 15 / 15 | 256 KiB | 3 932 160 | 23.4% | 0 | — |

四件事：

1. **余量随 `-j` 单调下降。** 段长随 `-j` 缩小，预算跟着缩小（½ 段长到 ¼ 段长），
   而"最长扫描"由行长决定、与 `-j` 无关。所以最紧的一档永远在最大的 `-j` 上，
   这也解释了 6.5 里 `-j 2` 与 `-j 4` 两行新旧完全相同——那一档的预算本来就被
   1 MiB 封顶，除数不是约束。
2. **行 4 KiB 那一组的余量是 64~256 倍。** 这个量级说明：对最常见的长行输入，
   预算离"不够用"还差两个数量级，1/4 在这里完全不构成约束，真正的约束是更长的行。
3. **行 64 KiB 那一组的余量降到 4 倍。** 这是被测到的、最紧的现实形态：
   预算 256 KiB、最坏距离 65 535。除数改成 8 就只剩 2 倍，改成 16（预算 64 KiB）
   这一组就会开始丢切点——`check_align_budget.sh` 的第四类输入（行 96 KiB）
   钉的就是这条边界。
4. **行 1 MiB 那一组全部放弃，白读 23%。** 段数退化为 1，程序随后走顺序路径，
   结果正确、慢十几毫秒。这就是 3.8 说的"纯损耗"的实测值，也是 6.5 那个全字母
   输入（24%）的温和版本。要消掉它只有一条路：把"切不动"的判断提前——但一次
   局部探测区分不了"这一带没有分隔符"与"整个文件没有分隔符"（3.8 末），
   所以它留在待办里，没有为了省十几毫秒去加一条会丢并行度的启发式。

**这三组数据不能用来比较 `-j` 的性能。** 第三组的 `-j` 完全是退化的（段数为 1），
前两组在 CI 的两三个核上也不足以摊开并行度。这里要的是确定值：段数、切除点数、
读取字节数、最长扫描。耗时列只说明"多读 23% 值多少毫秒"。

### 6.7 混合负载：任务划分方式的影响

前六节量的都是"某种输入形态下的吞吐"，没有一节量到**任务划分方式本身**。第六节末尾
那组 8 个等大的文件也量不到：按文件分发本来就均衡。要量它得用"一大一小"的输入，
这正是 `tests/bench_mix_weight.sh`（`make bench` 第五段）做的事。

输入：64 MiB 正常文本 + 7 个各 1 MiB 的小文件，`-j 8`。

- 64 MiB 文件切成 32 段（每段 2 MiB），7 个 1 MiB 的文件各是一个整文件任务，
  共 **39 个任务**（`TRACE` 报 `任务 39 个（huge 32 段 + 7 个整文件）`）；
- 老实现（一个文件一个任务）在这种输入上的完工时间有一个**明确的地板**：8 个任务
  里 64 MiB 那个独占一个线程从头做到尾，其余 7 个几十毫秒就结束，于是 wall 时间
  就是它的单线程耗时。这个量不是估算，直接测：`-j 1 huge.txt`。

数据（CI / ubuntu-22.04 / gcc 11.4.0，各 3 轮取平均，两次运行）：

| 配置 | 第一次 | 第二次 | 说明 |
|---|---|---|---|
| 顺序 | 239 ms | 206 ms | 8 个文件顺序扫一遍，共 71 MiB |
| `-j 1 huge.txt` | 215 ms | 185 ms | **老路径的完工时间地板** |
| `-j 8`（第八轮） | 86 ms | 75 ms | 39 个任务：32 段 + 7 个整文件 |
| 相对地板 | 2.50× | 2.46× | |
| 相对顺序 | 2.77× | 2.74× | |

**比值比绝对值稳得多**：同一份代码两次运行的绝对耗时差 13%（86 vs 75 ms），
比值只差 1.6%（2.50 vs 2.46）。原因是三行数据出自同一份输出的同一次运行——运行器
整体变慢时三行一起变慢，比值基本不动。这也是这一组比 6.3 更强的地方：6.3 里
"顺序 vs `-j 8`"的比值同样只在一次输出内部成立，而这里连"再准备一份老实现来对照"
都不需要，地板就是同一份二进制在 `-j 1` 下的耗时。

为什么不是 4×：运行器能提供的并行度在 4 线程附近就饱和（6.3 两次运行里 `-j 4`
与 `-j 8` 都只差 1~2%），8 个工作线程要在约 4 个 vCPU 上轮转；此外 39 次分派
（每次约 600 ns）与 32 次对齐扫描也在总时长里。这里不再往下归因——剩下的差距
与"共享型运行器上到底有几个核是空闲的"纠缠在一起，量不出干净的数。

一条附带的正确性核对：脚本跑完会用 `cmp` 比对 `-j 8` 与顺序的输出，不一致就以非零码
退出，所以这一组既是性能测量也是一条端到端断言。

## 7 实现记录：从单文件 demo 到模块

这个主题从一份 52 行的教学代码 `count.c` 开始，经过两轮改造才成为模块：

| 轮次 | 产物 | 规模 | 做了什么 |
|---|---|---|---|
| 起点 | 原版 `count.c` | 52 行 | 能跑，但有多处缺陷，且完全是 demo 形态 |
| 第一轮 | 单文件完善版 | 106 行 | 修掉全部缺陷，仍是单文件 |
| 第二轮 | **本模块** | 头文件 + 实现 + 驱动 + 测试 | 接口与实现分离，状态外置，可被独立链接 |

第一轮的成果保留在 git 历史里（提交 `cdb73f0`），第 6 节的性能对比仍会用到它。

### 7.1 起点：原版 `count.c`

```c
#define OUT     0
#define IN      1
#define INIT    OUT

int splite(char c) {                /* 手写字符表，只列了 9 个字符 */
    if ((' ' == c) || ('\n' == c) || ('\t' == c) ||
            ('\"' == c) || ('\'' == c) || ('+' == c) ||
            (',' == c) || ';' == c || '.' == c)
        return 1;
    else
        return 0;
}

int count_word(char *filename) {
    int status = INIT;
    int word = 0;

    FILE *fp = fopen(filename, "r");
    if (fp == NULL) return -1;

    char c;                          /* 用 char 接收 fgetc 的返回值 */
    while ((c = fgetc(fp)) != EOF) {
        if (splite(c)) {
            status = OUT;
        } else if (OUT == status) {
            status = IN;
            word ++;
        }
    }

    return word;                     /* fp 从未关闭 */
}

int main(int argc, char *argv[]) {
    if (argc < 2) return -1;         /* 静默退出，不提示 */
    printf("word: %d\n", count_word(argv[1]));
}
```

### 7.2 第一轮：修掉的缺陷

| # | 缺陷 | 依据与后果 | 处理 |
|---|---|---|---|
| 1 | `char c` 接收 `fgetc` 的返回值 | C11 7.21.7.1 规定 `fgetc` 返回 `int`，EOF 是负值；C11 6.2.5p15 规定 `char` 是否带符号由实现决定。x86 上 `char` 有符号、恰好存得下 -1，行为正确；ARM 等平台 `char` 无符号，EOF(-1) 截断成 255，与 EOF 永不相等 → **死循环** | 改用 `int` 接收；字节数据在扫描时显式转 `unsigned char` |
| 2 | 任何返回路径都不 `fclose` | 每次调用泄漏一个文件描述符。一次性程序看不出（进程退出时内核统一回收），放进长期运行的循环就是硬故障 | 由 `fopen` 所在的函数在每条返回路径上关闭 |
| 3 | 不检查返回值 | 文件打不开时返回 -1，被当作词数打印成 `word: -1`；`main` 永远返回 0，脚本无法检测失败 | 引入分类状态码，输出具体原因，退出码反映失败 |
| 4 | 只看 `EOF` 不看 `ferror` | `fgetc` 返回 `EOF` 有两种可能：正常读完、发生读错误。只看 `EOF` 会把读错误静默当成正常结束 | 检查 `ferror`，命中时报读错误 |
| 5 | 词数判据用手写字符表 | 原表只列了 9 个字符，`! ? - ( ) [ ] { } : / = < > \| @ # $ % ^ & * ~` 以及反引号全部漏掉，会把 `!`、`{-`、`}` 连成的串当成词 | 改为 `isalnum`，语义是"最长连续字母数字段"，定义完整无遗漏 |
| 6 | 计数器用 `int` | 常见平台上限 2147483647，处理语料库、日志聚合级别的输入会溢出 | 改用 `unsigned long`（LP64 下 64 位） |
| 7 | 只能处理单个文件，`argc < 2` 时静默 `return -1` | 用户看不到任何提示，不知道是参数没给还是文件有问题；不支持批量，也没有总计 | 遍历 `argv[1..argc-1]`，输出用法提示，多个文件时补 `total` 行 |
| 8 | `splite` 拼写错误，参数用 `char`；`OUT`/`IN` 用 `#define` | 函数名与被判断的语义不符（它判断的正是"是不是分隔符"）；`#define` 在预处理阶段无差别替换，没有类型、调试器看不见 | 改名 `is_separator`；常量改为 `enum`；内部函数保持 `static` |
| — | `main` 走到 `}` 结束，没有 `return` | **不构成缺陷。** C11 5.1.2.2.3 专门规定：`main` 执行到终结的 `}` 等价于 `return 0;`。这是标准为 `main` 开的特例，其他函数不享有 | 模块的 `main` 仍显式 `return failed;`，因为它的返回值承载了"是否有文件处理失败"的信息 |

第 1 条最需要留意：它在开发机上**完全看不出来**。x86 的 `char` 有符号，`-Wall -Wextra`
不报任何警告，程序行为也正确；只有 `-Wconversion` 能发现 `int` → `char` 的窄化转换。
同一份代码在 ARM 目标板上直接死循环。这正是 `-Wconversion` 值得长期开着的理由——
它抓的不是风格问题，而是开发机与目标平台的 ABI 差异。

关于第 8 行那条"不是缺陷"，有一个可观测的旁证：把 `main` 改名之后，GCC 立刻开始报警告——
`warning: control reaches end of non-void function [-Wreturn-type]`。因为在它眼里这已经
不是 `main` 了，特例不再适用。这也解释了原版在 `-Wall -Wextra` 下**完全零警告**的部分原因。

第 2 条和第 4 条在一次性小程序里都不会暴露。这是"能跑的代码"与"能用的模块"之间最典型的差距：
前者只需要在一条路径上正确，后者需要所有路径都正确。

### 7.3 第二轮：结构上的改变

第一轮结束时，代码是正确的，但仍然是 demo——要复用只能把整个 `count.c` 拷走。
第二轮解决的是"能不能被别人拿去用"：

| 单文件完善版 | 本模块 |
|---|---|
| 一个 `count.c` 包含全部逻辑 | `include/`（接口）+ `src/`（实现）+ `src/main.c`（驱动） |
| 只能统计单个文件，一次一个结果 | `wc_counter` 对象，可同时持有任意多个独立计数器 |
| 状态是 `count_word` 的局部变量，数据必须整体到手 | 状态存在对象里，可按任意粒度分块送入，结果不变 |
| 内部函数全部 `static`，外部无法复用 | 公开接口 + `libwordcount.a`，`main.c` 只链接不重编 |
| 手写测试，无自动化 | `make test`（40 项检查）+ `make check`（交叉验证）+ `make sanitize` |
| 手动 `gcc` 一行命令 | `Makefile`，目标拆分，零警告构建 |
| 错误只能用 `errno` 的原始值表达 | `wc_status` 枚举给错误分类，附 `wc_status_string` |

最关键的一步是**把扫描状态从函数局部变量提升为对象成员**。这不是"重构"式的整理，
而是能力上的变化：状态在局部变量里，函数就只能处理"已经完整到手"的数据；状态在对象里，
函数才能处理任意分段的流。后面所有的接口设计（`wc_counter_update` 的分块语义、
可重入性、多实例并存）都是从这一个决定推出来的。

### 7.4 第三轮：把并发接到驱动层

第三轮的目标不是"让模块支持多线程"，而是"让命令行在多个文件上有并行度"。
两者的差别决定了改动落点：

| 做法 | 后果 |
|---|---|
| 在 `wc_count_file` 内部加线程池 | 库被迫链接 pthread，单文件调用也要建池；接口语义从"数一个文件"变成"数一个文件，顺便管线程" |
| 在驱动层为每个文件提交任务 | 库一行不改，`wordcount.h` 不出现任何线程类型，并发策略完全属于调用方 |

选后者。改动集中在 `src/main.c`（任务与槽位的划分、顺序输出、错误顺序）与
`Makefile`（一条把 thread-pool 建到本模块 `bin/` 下的规则、`-pthread`、
`-D_POSIX_C_SOURCE=200809L` 给 `getopt`），`wordcount.c` 与 `wordcount.h` 没有任何改动。

这也顺带解释了为什么"模块之间协作"不等于"把两个模块的源码放进同一个仓库"：
真正接起来的那一刻，一定会出现接口方向、链接方式、构建依赖这三个具体决定，
而它们只能靠一个实际的使用场景来定。

### 7.5 第四轮：单文件切分

第三轮把并行度给了"多个文件"，单文件仍然是单线程（9.5 曾把这一条列在已知局限里，
并写明"先做边界对齐的正确性原型，再谈收益，不要先写线程池调用"）。第四轮按这个顺序做：

1. **先在库里放两个不碰线程的原语**：`wc_align_chunk`（找切点）与
   `wc_count_fd_range`（数一段）。它们的正确性可以完全脱离并发来验证——
   `tests/test_split.c` 在一个线程里顺序调用它们，把各段结果相加，
   与整文件结果比对 190 项。
2. **再让驱动层用线程池跑这些段**。驱动层的改动结构与第三轮同构：槽位、任务、
   主线程汇总，没有引入新的同步手法。

这个顺序不是形式。如果先写线程池调用，一旦结果不对，要区分"切点算错了"还是
"并发写坏了"就只能靠猜；而先固定住原语的语义（尤其是 `*out` 在错误时不被修改、
`errno == 0` 表示文件被截短），并发那一层就只剩"槽位有没有共享"这一个问题，
它也已经有 `threadpool_wait` 的 happens-before 保证。

附带的一条工程结论：**测试的判据要包括"被测路径真的走了"**。切分输出与顺序输出相同的
这条断言，在切分没发生时也成立，所以 `check_split.sh` 先用 `WORDCOUNT_TRACE_SPLIT`
断言段数 ≥ 2，再关掉它做逐字节比对。同类问题在 thread-pool 的 `make stress`
上也出现过（占位任务提前结束导致所有等待走快速路径，见该模块 CHANGELOG 2026-11-05）。

### 7.6 第五轮：给切点对齐加读取预算

第四轮把"切点必须落在分隔符上"做对了，但没有回答"找切点要读多少字节"。
第四轮的文档里写的是"一个 4 GB 的单词会让这个文件被读两次"——**这句是错的**。
对齐扫描对每个建议切点独立执行，第 k 个从 `k * size / nchunks` 读到 `size`，
`-j 16`（64 段）时合计 31.5 遍。错在一个默认前提上：以为"对齐一次"，
实际是"对齐 `nchunks - 1` 次，每次都可能走到文件末尾"。

第五轮只改驱动层，三个决定：

| 决定 | 理由 |
|---|---|
| 预算放在驱动层，库不动 | `wc_align_chunk` 的 `limit` 本来就是调用方给的；"找多久算太久"是策略，不是语义 |
| 超预算就丢切点，不夹紧 | 夹紧会把"库返回了 limit"这个事实抹掉，与第四轮拒绝夹紧是同一个理由 |
| 预算取 1 MiB | 段长下限也是 1 MiB；一个词长到 1 MiB 的输入本来就不该在它内部切 |

附带两件事，都和前几轮同源：

- **可观测量先行。** 加不加预算，输出逐字节相同，所以 `WORDCOUNT_TRACE_SPLIT`
  从"几个段"扩成四个数（段数、建议切点、接受、放弃、对齐读取字节数）。
  第四轮已经为这条付过一次学费（5.9），第五轮只是把它用到新功能上。
- **判据要能区分"功能生效"与"功能没生效"。** `check_align_budget.sh` 里
  "32 MiB 全字母文件的 15 个切点全部被放弃、只剩 1 段"这条，把预算删掉**也成立**
  （旧实现同样把切点全部推到文件末尾、同样只剩一段）。真正能区分的只有读取字节数：
  旧实现 240 MiB，新实现 15 MiB。段数、输出、退出码三者在这种输入上一个都不动，
  所以判据必须落在读取量上。

### 7.7 第六轮：预算随段长收缩

第五轮结尾留了一句话："**`一遍`这个上界不算小**，`-j 16` 那行是 98%。"
98% 不是测量误差，是策略本身的性质：预算按**每个切点**计，切点个数随 `-j` 增长，
总量于是随 `-j` 线性增长。固定预算只把"31.5 遍"压成"1 遍"，而"1 遍"这个上限
在 `-j` 大时会被用满。

第六轮把预算改成 `min(段长 / 4, 1 MiB)`，两个量各管一头：

| 量 | 管什么 | 不管会怎样 |
|---|---|---|
| `段长 / 4` | 总量封顶：`Σ budget_i ≤ Σ chunk_i / 4 = size / 4` | `-j` 越大读得越多，98% 那一行 |
| `1 MiB` 上限 | 单次不过分：段很大时预算不跟着膨胀 | 400 MiB / `-j 8` 会给每个切点 3.1 MiB，而 1 MiB 早就够 |

改动本身只有三行（循环外算 `chunk_bytes` 与 `align_budget`、循环内把
`ALIGN_SCAN_BYTES` 换成 `align_budget`），加上一个 `_Static_assert` 挡住
"除数改成让预算变 0"这种改法。库仍然一行未改——**预算始终是驱动层的策略**。

这一轮真正的产出不在代码上，而在**判据的分工**上。5.10 现在有两条不变量，
它们在注入验证里表现完全不同：

| 注入 | 公式断言失败 | 读取量断言失败 |
|---|---|---|
| 预算改回固定 1 MiB（`DIV = 1`） | 11 项 | 7 项 |
| 预算根本不用（`scan_to = size`） | **0 项** | 8 项 |

第二种最有价值：`TRACE` 把 `align_budget` 算对并打印出来，只是没有拿它去截断扫描。
一个只看"预算值对不对"的测试会全绿通过。**"算对了"与"用上了"必须分别断言**，
这和第五轮"功能生效与功能没生效必须能区分"是同一条原则的下一层。
（这次注入总数是 10 项而不是 8：除 8 条读取量断言外，还有 `longword` 那条
"应只放弃一部分切点"——没有预算时一个切点都不会被放弃，`放弃 0`。）

顺带一条方法上的补充：`tests/test_split.c` 里的 `chunked_stat_budget` 是驱动层策略的
**副本**，不是共享实现——副本能固定住策略的语义，但改坏驱动层时它一定跟着绿。
能抓住驱动层缺陷的只有 `check_align_budget.sh`（跑真二进制、读 `TRACE`）。
两者都要有，作用不同。

### 7.8 第八轮：任务单元从"一个文件"改成"一个字节区间"

第七轮的产出全在测量与判据上（5.10、6.6），没有新的实现记录可写，
这一节直接记第八轮。

到此为止，`-j` 有两条互斥的路径：多个文件时一个文件一个任务，单个文件时切成若干段。
两条路径各自都有测试，但"同时给多个文件、其中几个大到该切"这种组合根本没走过——
它是 9.5 最后一条与待办里挂了很久的那条：文件也拆成字节区间任务，共用一个队列。

改动集中在 `src/main.c`，库一行未改。三件事值得单独记：

**一、规划与执行分成两段，是为了让任务数在建池之前已知。** 第一版想边规划边提交，
写完发现线程数取不了 `min(JOBS, 任务数)`——提交时还不知道总共有多少个任务。
改成先 `plan_file()` 逐个文件产出区间（fd 与 `ranges[]` 挂在 `file_entry` 上），
再统一建 `tasks[]` 与排序表 `order[]`，最后一次性提交。代价是所有可切文件的 fd
在规划阶段就要打开并保持到任务结束（9.5 记了这条限制）。

**二、批次边界从"文件"变成"区间"之后，切点的正确性前提没有变，但多了一条**
"同一文件的多个任务并发读同一个 fd"。这条成立的依据是 `pread` 的语义：
它按绝对偏移读、不修改也不依赖文件偏移（POSIX.1-2008 `pread()`），
因此多个线程对同一个 fd 并发 `pread` 不需要额外同步。若用 `read` 就会互相抢偏移，
那是老代码里 `run_split_file` 已经避开的坑，这次只是从"一个文件一条路径"扩展到
"一条路径多个文件"。

**三、排序这一步是"带权重的调度器"的全部内容。** 原本以为要实现一个按字节数
分配的调度器，实际写下来发现不需要：任务长度已经等价于耗时，队列又是 FIFO，
按长度降序提交就落进了列表调度的 4/3 界里。真正需要写清楚的只有第二级比较
（等长任务按 `(文件, 段)`），因为 `qsort` 不稳定，只比长度会让提交次序依赖 libc。

测试上补的是"新路径真的被走到"这一类断言（`tests/check_mix.sh`，5.11 节）：
逐字节比对在"每个文件都退化成一个整文件任务"时同样全绿，所以必须把任务数、
切分记录条数与首个任务的字节数量出来。这与 5.9、5.10 记的两个假通过是同一条原则：
**先问这条断言在功能没生效时会不会也通过。**

## 8 词的定义与口径

同一份 `b.txt`，按不同的"单词"定义会得到不同的数字。列出这组数据是为了说明
**词数不是一个唯一定义的量**，任何一个数都得先说清楚口径：

| 定义 | 实现方式 | `b.txt` 结果 |
|---|---|---|
| 非空白段 | `wc -w`，`isspace` 判据 | 113550 |
| 非（空白或标点）段 | `isspace \|\| ispunct` 判据 | 115426 |
| 字母数字段 | 本模块，`isalnum` 判据 | **114588** |

第二行比第三行多出 **838** 个"词"。原因在字节口径：`b.txt` 含 8757 个非 ASCII 字节
（正文用了 UTF-8 弯引号），而在 C locale 下 `ispunct` 对 `0x80–0xFF` 一律返回 0——
这些字节既不是空白也不是标点，于是被当成"词字符"，一个孤零零的弯引号就成了一"个单词"。

以 `isalnum` 为判据时，`0x80–0xFF` 全部落在分隔符一侧，这 838 个幽灵词就消失了。
代价是弯撇号会把词切开：`don’t` 写作弯撇号时会被算成 2 个词。

本模块选择的口径是 **单词 = 最长的连续字母数字段**。它有两个好处：ASCII 下定义完整、
没有遗漏（第 7 节第 7 条缺陷正出自旧判据的遗漏）；高位字节的处理方向是"更保守"
（少算而不是多算），不会凭空造出词来。

## 9 已知局限

### 9.1 非 ASCII 字节一律当作分隔符

本模块是**字节导向**的，并且工作在 C locale 下。`isalnum` 对 `0x80–0xFF` 全部返回 0，
因此这些字节全部被当作分隔符。后果是双向的：

- 好的一面：孤立的 UTF-8 标点不会被误计成单词（第 8 节的 838 个幽灵词）。
- 不好的一面：带弯撇号的词会被切开，`don’t` 算 2 个词。

**严格的 UTF-8 处理需要另一套做法**：`setlocale(LC_ALL, "")` 打开区域设置，
用 `mbrtowc` 把字节流转换为宽字符，再用 `iswalpha` 判断——这是"按字符"而非"按字节"扫描，
代码量和复杂度都会明显上升，且引入对区域设置数据的运行时依赖。
本主题定位是字节流扫描的基础实现，不展开。

### 9.2 只统计总量，没有词频

当前只输出三个总数。若要统计每个词的出现频次（`sort | uniq -c` 那类场景），
需要一个"单词 → 计数"的映射表。C 里通常用哈希表实现，涉及哈希函数设计、冲突处理、
内存管理、大小写归一，是另一个量级的话题。

### 9.3 不预判输入类型

`fopen` 在 Linux 上也能打开目录，随后的读取会失败并设置 `errno = EISDIR`。
本模块会通过 `ferror` 报出 `Cannot read stream: Is a directory`，
但不会在打开之前把目录识别出来并给出更准确的提示。

### 9.4 大文件的 `bytes` 计数依赖平台

`unsigned long` 在 LP64 平台是 64 位，在 32 位平台（ILP32）上上限约 42.9 亿字节，
即单个文件超过 4 GiB 时 `bytes` 会回绕。需要跨平台一致的行为时应改用 `uintmax_t`。
`lines` / `words` 在 32 位平台上的上限同样是 42.9 亿，对绝大多数文本足够。

### 9.5 切分的边界条件仍有一串限制

不小于 2 MiB 的普通文件会被切段并行（3.7 节、6.4 节），并且第八轮起它与"多个文件"
不再互斥：同一批里几个大文件各自切段，与小文件一起进同一个队列。切分仍只在这些
条件下成立：

- **只对普通文件。** 管道、终端、目录、设备文件都不切。管道与终端不可 `lseek`，
  也没有"文件总长度"这个概念；目录的 `st_size` 是实现相关的，拿它算切点没有意义。
  这些输入仍然走顺序路径，只是 `-j` 对它们无效。
- **只对不小于 2 MiB 的文件。** 更小的文件里，`open` + 建池 + 对齐扫描的固定成本
  与扫描本身同量级，切了反而慢。这个门槛是实测选的（6.4 节末尾），不是理论推导。
- **整段落在同一个超长单词里时不切。** 建议切点要么被对齐一路推到文件末尾，
  要么在预算内找不到分隔符而被直接放弃，`ntasks` 只剩 1，驱动退回顺序路径。
  正确性没问题，但这条路径的开销全在"找切点"上：预算按 `min(段长 / 4, 1 MiB)` 给
  （3.8 节），所以总读取量封顶在 `size / 4`。64 MiB 全字母文件、`-j 16` 时实测读
  16 515 072 字节（文件的 24%），之后还要顺序再读一遍（6.5 节）。剩下的 24% 是
  **纯损耗**——这个文件根本切不动，读它是为了确认"切不动"。要省掉它，得在第一个切点
  被放弃时就中止整轮对齐（待办）。
- **行长超过预算的文件同样切不动。** 上一条说的是"整个文件没有分隔符"，边界情况是
  "分隔符存在但比预算稀疏"：16 MiB、每行 1 MiB 的输入在 `-j 16` 上 15 个建议切点
  全部被放弃，段数 1，代价是读掉 3 932 160 字节（23%）之后仍然走顺序路径（6.6 节）。
  可见的边界在行长 ≈ 预算（256 KiB）附近：行 64 KiB 时余量 4 倍，行 96 KiB 时
  `check_align_budget.sh` 仍要求不丢切点。
- **段数上限 `jobs × 4` 是逐文件算的，每段不小于 1 MiB。** 单个 400 MB 的文件在
  `-j 256` 下最多切 1024 段，更大的文件段会变大而不是变多；同时给 8 个各 400 MB 的
  文件、`-j 8` 则会得到 8 × 32 = 256 个任务。整个队列的任务数没有独立上限，
  它由"每段不小于 1 MiB"这条下限间接约束（任务数 ≤ 总字节数 / 1 MiB）。这样定的理由是
  让每段的固定成本占比可控；代价是超大文件在极高 `-j` 下仍有均衡问题。
- **同时打开的文件数等于可切文件数。** 规划阶段为每个可切文件 `open` 一次并保持到
  全部任务结束，这样任务读到的正是 `fstat` 过尺寸的那个 inode，不会出现"规划时是 A、
  执行时已被换成 B"的窗口。代价是文件很多时可能撞上 `RLIMIT_NOFILE`（Linux 默认 1024），
  此时那些文件报 `cannot open file: Too many open files` 并以非零码退出，而不是
  静默退回单线程。整文件任务不占这个配额——它们在任务里按路径打开、读完就关。
- **切点对齐的代价与被切内容有关。** 正常文本里分隔符平均每 5~6 字节出现一次，
  对齐只读几个字节——8.2 MiB 文本、7 个建议切点，合计读不到 1 KiB（5.10 节的断言
  上限就是 64 KiB）。分隔符越稀疏读得越多，最坏情况见上面第三条与 3.8 节。

### 9.6 并行不覆盖标准输入

管道和终端不可 `lseek`，只能顺序读一遍，因此 `-j` 在读标准输入时无效（仍走顺序路径）。
这也意味着 `cat *.log | wordcount -j 8` 不会变快——想并行就得让程序自己 `open` 文件。

      确认块读取在大文件上是否仍是瓶颈
- [ ] 为 `wc_count_stream` 补一个 `EINTR` 重试用例（`pread` 那条路径已经重试，
      stdio 那条仍在假设它自己处理了中断）
- [x] 单文件内部按块并行（第四轮）：`wc_align_chunk` + `wc_count_fd_range`
      两个原语，驱动层按分隔符对齐切段交给线程池。190 项切分测试 +
      87 项命令行比对，单核下切分开销测不出来（6.4 节）
- [x] 把"多文件 + 切分"合成一条路径（第八轮）：任务单元改成"某个文件的一个字节区间"，
      全部进同一个池，按任务字节数降序提交（LPT）。规划与执行分成两段，线程数取
      `min(-j, 任务数)`。`tests/check_mix.sh` 24 项进 `make check`，
      `tests/bench_mix_weight.sh` 量 1 × 64 MiB + 7 × 1 MiB 的完工时间（6.7 节）
- [ ] LPT 拿字节数当耗时，但两种读法的单位字节成本不同：区间任务走 `pread`，
      整文件任务走 stdio `fread`（多一次内核缓冲区到 stdio 缓冲区的拷贝）。等长的
      两类任务里，stdio 那个更慢，权重按说该乘一个系数。要量这个比值只能写一个小
      测试程序：命令行上"要不要切分"由文件大小决定（不小于 2 MiB 必走区间），
      同一份数据没法在两条路径上各跑一次
- [ ] 可切文件的 fd 全部保持打开，文件很多时撞 `RLIMIT_NOFILE`（9.5）。
      可选做法：先 `getrlimit` 探一个上限，超出时把多出来的文件降级成整文件任务
- [x] 对齐扫描加读取上限（第五轮）：每个建议切点给 1 MiB 预算，预算内找不到分隔符
      就放弃这个切点、把它并进前一段。`tests/test_split.c` 增 17 项（190 → 207），
      新增 `tests/check_align_budget.sh`（17 项比对），对齐读取总量封顶在一遍文件
      （3.8 / 6.5 节）。库接口未变
- [x] 预算随段长收缩（第六轮）：改成 `min(段长 / 4, 1 MiB)`，总量上界从"一遍文件"
      收紧到 `size / 4`，且与 `-j` 无关。64 MiB 全字母文件 `-j 16` 的对齐读取
      从 98% 降到 24%，同机耗时 213 → 169 ms（6.5 节）。`tests/test_split.c`
      207 → 226 项，`check_align_budget.sh` 17 → 41 项（新增预算公式核对与
      不变量 `Σ读取 ≤ size / 4`）
- [ ] 在第一个切点就被放弃时中止整轮对齐——`size / 4` 已经是硬上界，但代价现在有
      实测了：16 MiB、行 1 MiB 的输入在 `-j 16` 上白读 3 932 160 字节（23%，十几毫秒），
      64 MiB 全字母文件是 24%（6.5 / 6.6 节）。难点不在省这十几毫秒，而在一次局部探测
      区分不了"这一带没有分隔符"与"整个文件没有分隔符"，猜错的代价是整个文件退回
      单线程，比十几毫秒大得多
- [x] 补一组"行很长的日志 / CSV"的实测（第七轮）：`tests/bench_align_sparse.sh`
      造行 4 KiB / 64 KiB / 1 MiB 三类输入，用新增的"接受切点最长扫描"量出预算余量。
      结论：预算 256 KiB 覆盖到行长 ≈ 256 KiB；行 64 KiB 余量 4×、行 4 KiB 余量 64×、
      行 1 MiB 全部放弃（6.6 节）。除数仍取 4，理由与代价写在 3.8
- [ ] 给稀疏分隔符那组加 128 KiB / 256 KiB 两档行长，把"覆盖边界在行长 ≈ 预算"从
      推断变成实测的一个点
- [ ] 段数上限 `jobs × 4` 是按经验定的，可以改成"按文件大小与每段最小字节数取大"
- [ ] `-j` 支持"不带数字时取 CPU 核数"（`sysconf(_SC_NPROCESSORS_ONLN)`），
      但要先确认"用满核数"在超线程机器上不是负收益
