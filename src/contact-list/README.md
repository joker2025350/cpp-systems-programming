# 04 通讯录（contacts 模块）

一个可复用的通讯录模块，加一个建立在它之上的命令行驱动。

模块内部同时维护两份结构：双向链表保存插入顺序，哈希索引保存"姓名 → 节点"的映射。
核心是三条约定：`name` 作为主键保证查找与删除的结果唯一；链表维护 `head` 与 `tail`
两个指针，使追加是 O(1) 且遍历顺序等于插入顺序；写出的文件格式一定能被自己的读取器原样读回。

索引不影响任何函数的语义——`contacts_find` 仍然只回答"找到"或"没找到"。
它带来的是复杂度变化：查找、查重、删除从 O(n) 变成 O(1) 均摊，批量构建从 O(n²) 变回 O(n)；
代价是每个节点多一个指针，再加一张桶表。第 6 节给出同一台机器上两种方案的实测对比。

`include/` 与 `src/` 分离，`main.c` 只通过 `libcontacts.a` 链接，不重复编译模块源码——
"这个模块能被独立链接使用"这件事在每次构建时都会被动验证一遍。

```bash
$ ./bin/contacts -f book.txt add alice 13900001111
$ ./bin/contacts -f book.txt add bob 13800002222
$ ./bin/contacts -f book.txt list
name: alice, phone: 13900001111
name: bob, phone: 13800002222
$ ./bin/contacts -f book.txt find bob
name: bob, phone: 13800002222
```

## 2 对外接口

### 2.1 数据结构

```c
typedef struct contact {
    char name[CONTACT_NAME_MAX];      /* 64 字节，含 '\0' */
    char phone[CONTACT_PHONE_MAX];    /* 64 字节，含 '\0' */
    struct contact *prev;
    struct contact *next;
    struct contact *hash_next;        /* 索引桶链，模块内部维护 */
} contact;

typedef struct {
    contact *head;      /* 表头 */
    contact *tail;      /* 表尾 */
    size_t   count;     /* 节点数量 */
    contact **buckets;  /* 桶数组，长度是 2 的幂；NULL 表示还没有索引 */
    size_t   nbuckets;
} contact_book;
```

结构体成员是公开的，为的是让调用方能在栈上直接分配 `contact_book`——
嵌入式环境下不希望在打开一个通讯录时还依赖堆。但约定不直接读写其中字段，
一律通过下面的函数访问。后三个字段（`buckets` / `nbuckets` / `hash_next`）
是索引的实现细节，公开只因为 C 里没有"私有成员"这回事。

1.1.0 加入索引之后，`contact` 与 `contact_book` 的尺寸都变了（64 位下
`contact` 从 136 字节到 152 字节），因此**库与调用方必须一起重编**：
源码级兼容，ABI 不兼容。这一点写进头文件的版本注释里，不靠使用者自己发现。

两个容量宏也是公开的，调用方可以直接用 `CONTACT_NAME_MAX` 声明临时缓冲区，
不必硬编码一个数字——硬编码的后果是模块扩容后调用方的缓冲区悄悄变小，而编译器不会报警。

### 2.2 状态码

```c
typedef enum {
    CONTACTS_OK             = 0,   /* 成功 */
    CONTACTS_ERR_PARAM      = 1,   /* 参数非法，例如传入了 NULL */
    CONTACTS_ERR_NOMEM      = 2,   /* 内存分配失败 */
    CONTACTS_ERR_OPEN       = 3,   /* 无法打开文件 */
    CONTACTS_ERR_READ       = 4,   /* 读取过程中出错 */
    CONTACTS_ERR_WRITE      = 5,   /* 写入或改名失败 */
    CONTACTS_ERR_CLOSE      = 6,   /* 关闭文件时出错 */
    CONTACTS_ERR_FORMAT     = 7,   /* 字段内容不符合格式约定，或行无法解析 */
    CONTACTS_ERR_TOOLONG    = 8,   /* 字段超出容量 */
    CONTACTS_ERR_NOTFOUND   = 9,   /* 没有这个联系人 */
    CONTACTS_ERR_DUPLICATE  = 10   /* 姓名已存在 */
} contacts_status;
```

沿用 C 语言的惯例：0 表示成功，非 0 表示失败。`CONTACTS_OK` 固定为 0，
因此可以直接写 `if (status)` 判断失败。

`CONTACTS_ERR_FORMAT` 与 `CONTACTS_ERR_TOOLONG` 分开是有必要的：前者是"字段内容
里有逗号或者整行缺字段"，后者是"字段太长"。驱动层据此给出不同的提示，
用户才知道该改内容还是改长度。

### 2.3 生命周期

| 函数 | 作用 |
|---|---|
| `void contacts_init(contact_book *book)` | 初始化为空表，栈上分配之后必须先调用 |
| `void contacts_clear(contact_book *book)` | 释放全部节点，回到空状态，可重复调用 |
| `void contacts_destroy(contact_book *book)` | `contacts_clear` 的别名，表达"这本书到此为止" |
| `size_t contacts_count(const contact_book *book)` | 返回数量，`book` 为 NULL 时返回 0 |

### 2.4 增删查

| 函数 | 说明 |
|---|---|
| `contacts_status contacts_add(book, name, phone)` | 追加到表尾；重名返回 `DUPLICATE` |
| `contacts_status contacts_remove(book, name)` | 按姓名删除；找不到返回 `NOTFOUND` |
| `const contact *contacts_find(book, name)` | 按姓名查找；找不到返回 NULL |

`contacts_add` 对字段的要求是：非空、长度小于容量、不含逗号与换行符。
这三条不是随手定的，理由见 3.3 与 3.4。

`contacts_find` 是平均 O(1) 的：按姓名算哈希、取桶、在桶链上比较。最坏情形是 O(n)，
前提是大量姓名落在同一个桶上（见 9.7 的哈希洪泛）。索引不改变返回值，
也不改变"找不到返回 NULL"这一条。

返回的 `const contact *` 在下一次 `contacts_remove` / `contacts_clear` 之前保持有效。
追加不会移动已有节点，所以已有的指针在 `contacts_add` 之后仍然可用；
索引扩容只在桶链上重排，同样不动节点本身。
只有删除和清空才会让它失效。

### 2.5 遍历

游标式，而不是"传一个回调函数进去"：

```c
for (const contact *c = contacts_first(book); c != NULL; c = contacts_next(c)) {
    printf("%s %s\n", c->name, c->phone);
}
```

选游标而不选回调，有两个原因：调用方可以在任意位置提前结束，不需要靠回调的返回值
表达"停下来"；也不需要为每种用途定义一个回调类型。遍历顺序是插入顺序。
遍历期间不要增删节点，否则游标会失效。

### 2.6 文件存取

```c
contacts_status contacts_save(const contact_book *book, const char *path);

contacts_status contacts_load(contact_book *book, const char *path,
                              contacts_load_mode mode,          /* APPEND / REPLACE */
                              contacts_load_result *result);    /* 可以为 NULL */
```

`contacts_load_result` 报告这次载入发生了什么：

```c
typedef struct {
    size_t loaded;            /* 成功载入的条数 */
    size_t skipped;           /* 跳过的行数 */
    size_t first_bad_line;    /* 第一个被跳过的行号，0 表示没有 */
} contacts_load_result;
```

`skipped` 只统计"有内容但不合法"的行，空行被静默忽略、不计入。
把这三个数暴露出来，是因为载入是唯一一个"部分成功"是常态的操作——
调用方需要知道是全部读进来了，还是有一部分被丢掉了。

内存不足是唯一会打断这个"部分成功"模式的错误：`contacts_add` 返回
`CONTACTS_ERR_NOMEM` 时 `contacts_load` 立即中止并同样返回 `NOMEM`，
`loaded` 是中止前真正读进来的条数，`skipped` 保持 0。
不把剩下的行记成"坏行"再返回 `CONTACTS_OK`，是因为调用方无法从
"skipped 很大"里区分"文件里有很多坏行"与"进程快没内存了"，而两者的处置完全不同。

### 2.7 辅助

| 函数 | 作用 |
|---|---|
| `const char *contacts_status_string(status)` | 状态码转可读描述，未知值返回 `"unknown status"`，不会返回 NULL |
| `contacts_status contacts_check_field(value, capacity)` | 单独校验一个字段，供驱动层给出针对性提示 |

`contacts_status_string` 保证不返回 NULL，是为了让调用方能直接写
`printf("%s", contacts_status_string(s))` 而不用先判空。

### 2.8 索引诊断

```c
typedef struct {
    size_t buckets;      /* 桶数量，0 表示还没有索引 */
    size_t entries;      /* 索引里挂着的节点总数 */
    size_t used;         /* 非空桶数量 */
    size_t max_chain;    /* 最长的一条桶链上的节点数 */
} contacts_index_stats;

contacts_status contacts_index_get(const contact_book *book,
                                   contacts_index_stats *out);
```

索引是内部实现，正常调用方不需要它。这组接口存在的理由只有一个：
让"索引与链表是否还一致""桶的分布是否合理"变成可以被测试断言的事实，
而不是靠"跑得快所以大概是对的"来推断。

`entries` 与 `contacts_count` 不相等，说明两份结构已经不一致——这是不变量，
不是可以忽略的统计噪声。测试与基准都靠它拿到实测的装载因子与最长链。

## 3 设计要点

### 3.1 维护 `tail`：顺序与复杂度是同一个决定

只保存 `head` 也能实现插入，但只有两种写法：

- **头插**：O(1)，但遍历顺序与插入顺序相反。这是最开始那版的写法。
- **走到表尾再插**：顺序正确，但每次插入是 O(n)，批量构建变成 O(n²)。

再存一个 `tail` 指针，两个问题一起消失：追加是 O(1)，顺序就是插入顺序。

这一点的影响比看起来大。头插法下 `save` 写出的文件也是倒序，读回来再存一次，
顺序又反一遍——文件内容会随往返次数振荡。而顺序一旦和插入顺序不一致，
"把通讯录导出成文件"这件事就没有稳定结果，比较、diff、增量同步都做不了。

代价是删除时必须同时维护 `tail`。删除一个节点有四种位置：表头、表中、表尾、唯一节点。
下面五行覆盖全部情形：

```c
if (item->prev != NULL) item->prev->next = item->next;
else                    book->head = item->next;

if (item->next != NULL) item->next->prev = item->prev;
else                    book->tail = item->prev;
```

`else` 分支处理的是"被删的是第一个/最后一个"。唯一节点会同时走进两个 `else`，
`head` 与 `tail` 一起变成 NULL，不需要额外的特判。

### 3.2 `name` 作主键

同一个通讯录里不允许重名，`contacts_add` 遇到重名返回 `CONTACTS_ERR_DUPLICATE`。

这条约束换来的是接口的确定性：`contacts_find` 与 `contacts_remove` 都按姓名定位，
如果允许重名，删一个 `alice` 到底删的是哪一个就没法回答了。要么在接口上加"删第几个"，
要么在文档里写"删除第一个匹配的"——后者是隐含契约，调用方很容易忽略。

代价是每次添加都要查重。纯链表实现下这是一次全表扫描，批量构建退化为 O(n²)，
第 6 节有实测数据；加入索引之后查重是 O(1)，代价变成每个节点多一个桶链指针，
以及一张 8 字节/桶的桶表。也就是说：**主键约束真正的代价不是"慢"，而是"必须有索引"。**

### 3.3 一个能被自己读回来的格式

写出的每一行固定是：

```
name: <姓名>, phone: <电话>
```

这条规则看起来平淡，但它是整个模块最重要的一条契约：**保存与读取必须互逆**。
每一次"保存 → 读取"，得到的内容都必须与保存前逐字节相同。

最初那版没有做到，实测：

```
保存到 rt.txt：
    name: alice, phone: 13900001111

读回后遍历输出：
    name: alice,phone: phone:13900001111
```

电话号码前面多了一个 `phone:`。原因是保存时逗号后带了一个空格，而解析器把
"逗号后的第一个空格"当成了字段名与值的分隔符，于是把 `phone:` 连标签一起吞进了值里。
每往返一次就多一层前缀，反复存几次之后号码变成 `phone: phone: phone:139...`。

这个缺陷不触发任何 sanitizer——从内存安全角度看没有任何越界，所有缓冲区都在范围内，
只是数据被悄悄地改错了。**这类缺陷只能靠"往返测试"发现**：保存、清空、读回、逐字段比较。

### 3.4 按标签定位，不按空格位置

解析器不依赖"第一个空格在哪"，而是先找标签的冒号：

```c
/* 第一个字段：行首到第一个冒号（冒号之前不能先出现逗号） */
p = line;
while (*p != '\0' && *p != ':' && *p != ',') p++;
if (*p != ':') return CONTACTS_ERR_FORMAT;

/* 值 = 冒号之后到第一个逗号，去掉两端空白 */
```

标签文本本身不参与语义，只看冒号。因此下面三种写法都能正确解析：

| 行 | 解析结果 |
|---|---|
| `name: liaoqf,telephone: 23456543789` | `liaoqf` → `23456543789` |
| `name: liaoqf, telephone: 23456543789` | `liaoqf` → `23456543789` |
| `name: liaoqf, phone: 23456543789` | `liaoqf` → `23456543789` |

而原来的"按第一个空格切"只能正确处理第一种。`testdata/c.txt` 就是第二种写法，
旧实现实测输出 `king --> phone:344567754`，新实现输出 `king --> 344567754`。

**写入端只用一种格式，读取端接受多种**——这是所有长期存在的文本格式的通用做法：
新版本写出的东西老版本读不了可以接受，老版本留下的文件新版本必须还能读。

### 3.5 字段里禁止逗号

既然逗号是字段分隔符，字段内容里就不能出现逗号，否则写出去的行再也无法唯一解析。
`contacts_check_field` 在入口处拒掉含 `,` `\n` `\r` 的值。

另一条路是转义：把逗号写成 `\,`，读取时再还原。但通讯录的姓名和电话本来就不需要逗号，
为了一个不存在的需求引入转义规则，会让格式变复杂、让解析器出错的概率变高。
**约束数据比给数据加语法便宜得多。**

电话里的 `+`、`-`、`()` 都是允许的（`+8613800002222`、`010-12345678` 都能存），
只有真正会破坏格式的三个字符被禁止。

### 3.6 原子写入：先写临时文件再改名

```c
n = strlen(path) + sizeof ".tmp";
tmp = malloc(n);
snprintf(tmp, n, "%s.tmp", path);

fp = fopen(tmp, "w");
/* ... 逐行写 ... */
fclose(fp);
rename(tmp, path);      /* POSIX 上原子替换 */
```

直接往目标文件里写，中途失败（磁盘满、进程被 kill、断电）会留下一个被截断的文件，
原来的内容已经没了。写成"临时文件 + rename"，失败时目标文件保持原样，
最坏情况只是多出一个残留的 `.tmp`。

`rename` 在同一个文件系统内是原子操作，所以临时文件必须放在目标文件所在目录，
不能放 `/tmp`——跨文件系统时 `rename` 会返回 `EXDEV`，退化成"拷贝再删除"，原子性就没了。
这也是为什么临时文件名是 `path + ".tmp"` 而不是 `mkstemp` 加上某个全局临时目录。

代价是要求目标目录可写，而不只是目标文件可写。这一点写在头文件的注释里。

### 3.7 坏行只跳过，不中断整个载入

一个格式不对的行不应该让另外 999 行都读不进来。`contacts_load` 的处理是：
跳过该行、计入 `skipped`、记录第一个坏行的行号，然后继续。

```c
if (parsed != CONTACTS_OK
    || contacts_check_field(name, CONTACT_NAME_MAX) != CONTACTS_OK
    || contacts_check_field(phone, CONTACT_PHONE_MAX) != CONTACTS_OK) {
    local.skipped++;
    if (local.first_bad_line == 0) local.first_bad_line = lineno;
    continue;
}
```

只有文件级错误（打不开、读出错、关闭出错）才返回非 0 状态码。

有一类坏行需要单独处理：**超过缓冲区长度的行**。`fgets` 读满缓冲区时不会带换行符，
剩下的字节还在流里。如果直接当下一行处理，一行坏数据会变成两行"看起来正常"的数据——
比直接丢掉的危害大得多。所以检测到这种情况时，把该行剩余字节吃掉，整行作废：

```c
if (len == sizeof line - 1 && line[len - 1] != '\n') {
    int ch;
    while ((ch = fgetc(fp)) != EOF && ch != '\n') { }
    local.skipped++;
    continue;
}
```

### 3.8 `errno` 的保存与恢复

```c
saved = errno;
if (fclose(fp) != 0 && status == CONTACTS_OK) {
    status = CONTACTS_ERR_CLOSE;
    saved  = errno;
}
if (status == CONTACTS_OK && rename(tmp, path) != 0) {
    status = CONTACTS_ERR_WRITE;
    saved  = errno;
}
errno = saved;
```

`fclose` 会刷新缓冲区、可能触发实际的 `write` 系统调用，因此它**可能改写 `errno`**。
先读 `errno` 再 `fclose`，读到的可能是关闭阶段的错误号，把真正的失败点覆盖掉；
`fclose` 成功时还可能把 `errno` 改成一个与本次失败无关的残留值。

驱动层还有一个配套判断：

```c
static int has_errno(contacts_status status) {
    return status == CONTACTS_ERR_OPEN || status == CONTACTS_ERR_READ
        || status == CONTACTS_ERR_WRITE || status == CONTACTS_ERR_CLOSE;
}
```

只有文件级错误才去 `strerror(errno)`。参数错误、重名、格式错误这三类的 `errno`
是上一次系统调用的残留值，照着它打印会输出一句与本次失败毫不相干的话。

### 3.9 `contacts_check_field` 单独暴露

"字段不合法"和"重名"需要给用户不同的指引：前者要改内容，后者要么改名要么先删。
如果模块只返回一个笼统的失败，驱动层要么重复实现一遍校验逻辑，要么给出含糊的提示。
把校验函数单独暴露，驱动层就能在调用 `contacts_add` 之前先判断是哪一类问题——
校验逻辑仍然只有一份。

### 3.10 哈希索引：为什么是分离链接，为什么不重排链表

索引要解决的问题只有一个：把"按姓名定位节点"从"扫一遍链表"变成"算一个下标"。
下面每个决定都有明确的取舍，不是默认选项。

**分离链接（separate chaining），不是开放寻址（open addressing）。**
开放寻址把元素存在桶数组里，删除时需要墓碑标记或向后搬移，而且扩容必须重算全部元素。
分离链接的每个节点本来就存在，索引只需要在节点上多挂一个 `hash_next`。
删除时改两个指针即可，不需要墓碑，也不需要搬移。代价是每条链多一次指针解引用
（一次可能的 cache miss），换来的是删除逻辑与链表删除同构——这是"两份结构的维护成本"
最要紧的一条：**能用一个模式写两遍的东西，不要用两个模式写一遍。**

**桶数取 2 的幂，用按位与取代取模。**
`nbuckets - 1` 掩码只在除数是 2 的幂时等价于取模。取模在 x86 上是 `div`，
20~40 个周期；只在除数是编译期常量时编译器才把它换成乘法。桶数在运行期变化，
编译器替代不了，所以用掩码。

这个选择带来的要求是：哈希函数的**低位**必须均匀。这决定了哈希函数不能随便选（见下条）。

**FNV-1a，不是 djb2，也不是运行期随机的 SipHash。**

```c
uint64_t hash_name(const char *name) {
    uint64_t h = 0xcbf29ce484222325u;         /* FNV 偏移基 */
    for (const unsigned char *p = (const unsigned char *)name; *p; p++) {
        h ^= (uint64_t)*p;
        h *= 0x100000001b3u;                  /* FNV 质数 */
    }
    return h;
}
```

三条理由：

1. **逐字节**，不需要预先知道长度，也不需要处理对齐。姓名是 `char[64]`，
   实际长度随内容变化，先 `strlen` 再按字处理（如 MurmurHash 那种）要多扫一遍。
2. **乘数是奇数**（`0x100000001b3` 的低字节 `0xb3`）。若乘数是偶数，
   每步乘法都会把最低位置 0，低位熵被逐位清空，用低位取下标就会退化成"全部挤在少数桶里"。
   这是选乘数时必须满足的条件，与"看起来随机"无关。
3. **不带随机种子**，因此同一批姓名每次都落在同一组桶里：测试能断言装载因子与最长链，
   基准的两次运行可以直接比较。代价见 9.7。

**装载因子不超过 1.0，扩容按 2 倍翻。**
`index_prepare` 在"插入后条数 > 桶数"时扩容。装载因子 1.0 对应平均链长 1，
成功查找的期望比较次数是 `1 + α/2`。实测 64000 条时装载因子 0.98、最长链 7 条
（第 6 节），说明 FNV-1a 在这批姓名上的分布是均匀的。

**扩容失败只降级，不失败。** 这段逻辑值得单独看：

```c
{
    contact **fresh = buckets_alloc(want);

    if (fresh == NULL) {
        return 0;       /* 降级：旧表继续用，语义不变 */
    }
    ...
}
```

桶数不足的后果只是链变长、查找常数变大，结果仍然正确。为了让一次纯性能优化
去否决一次合法的插入，是把可用性问题变成正确性问题。反过来，**首次建索引失败
必须上报 `CONTACTS_ERR_NOMEM`**：没有索引功能上仍然可用（`contacts_find` 有线性回退），
但那样等于把 O(n²) 的行为悄悄还给调用方，比直接报错更难排查。

**重挂桶链时只改 `hash_next`，不动 `prev` / `next`。**
如果扩容时按桶顺序重排链表，遍历顺序就不再等于插入顺序，`save` 写出的文件也跟着变——
一条会破坏第 3.3 节文件契约的捷径。索引可以随便重排，链表不行，这个边界必须守住。

**删除用二级指针拆链。**

```c
link = &book->buckets[bucket_index(book->nbuckets, name)];
while ((item = *link) != NULL && strcmp(item->name, name) != 0) {
    link = &item->hash_next;
}
*link = item->hash_next;
```

`link` 存的是"指向本节点的那个指针"的地址——可能是桶数组里的一格，也可能是前驱的
`hash_next`。用二级指针之后，"删链首"与"删链中间"是同一段代码，不需要分支。

**分配顺序：先索引、后节点。**
`contacts_add` 里 `index_prepare` 在 `malloc` 节点之前。反过来也会 work，但会产生
"节点已分配、索引建不起来"的状态，那时只能把节点释放掉再返回失败；现在节点分配失败时
桶表是一张空表，仍然自洽。分配顺序决定了失败时的可达状态数量，越少越好。

## 4 构建

```bash
make            # 构建静态库 bin/libcontacts.a 与命令行工具 bin/contacts
make lib        # 只构建静态库
make cli        # 只构建命令行工具
make test       # 构建并运行单元测试 + 分配失败注入测试
make test-alloc # 只跑分配失败注入测试
make check      # 命令行端到端验证
make sanitize   # 用 ASan + UBSan 重新构建并跑测试，产物在 bin/sanitize/
make bench      # 不同规模下的耗时
make clean      # 删除 bin/（含全部变体）
```

`test_alloc` 与其余测试的构建方式不同：它要 `-Wl,--wrap=malloc -Wl,--wrap=calloc`。
`--wrap` 只重定向**未定义引用**，所以 `libcontacts.a` 里对 `malloc` / `calloc` 的调用
会绕到测试文件定义的 `__wrap_*`，而 libc 内部的分配（比如 `fopen` 的 stdio 缓冲区）
不受影响。这正是需要的粒度：注入的是模块自己的分配，不是整个进程的。

变体构建使用独立输出目录，是因为 make 判断是否重建只比较时间戳、不比较编译选项：
共用 `bin/` 时先跑 `make sanitize` 再跑 `make`，普通构建会认为目标已是最新，
留下一个插桩过的可执行文件，运行时报链接期符号错误。

默认编译参数：

```make
CFLAGS   ?= -std=c11 -Wall -Wextra -Wconversion -O2 -g
CPPFLAGS += -Iinclude
```

| 参数 | 作用 |
|---|---|
| `-std=c11` | 固定语言标准，避免依赖编译器的默认方言 |
| `-Wall -Wextra` | 常规警告集；本主题里有一处 `int` 函数缺 `return` 的缺陷只有它能发现 |
| `-Wconversion` | 检查隐式窄化转换。`fgets` 的长度参数、`snprintf` 的缓冲区大小都在 `size_t` 与 `int` 之间来回，打开它能防住静默截断 |
| `-O2` | 优化；模块不依赖任何未定义行为，优化不会改变结果 |
| `-g` | 保留调试信息，配合 `make sanitize` 时能定位到具体行 |

`CFLAGS ?=` 是条件赋值，可以在命令行上覆盖：

```bash
make CFLAGS="-std=c11 -Wall -Wextra -Wconversion -O0 -g -funsigned-char"
```

**把模块当库用：**

```bash
cc -std=c11 -Wall -Wextra -Wconversion -O2 -Iinclude your_app.c bin/libcontacts.a -o your_app
```

静态库要放在引用它的目标文件之后——`ar` 生成的库按需抽取成员，顺序反了会报未定义符号。

### 5.5 分配失败注入

`make test-alloc`，410 项检查：

```
contacts 分配失败注入测试

      扫描了 9 个分配点

410 项检查，0 项失败
```

普通用例无法覆盖 `malloc` 返回 NULL 这条路径：它取决于此刻的可用内存，
也不能靠写一个巨大的分配请求去逼近——那会让行为依赖 overcommit 策略，
在容器里与物理机上不一样。所以改成注入：`tests/test_alloc.c` 定义
`__wrap_malloc` / `__wrap_calloc`，链接时用 `--wrap` 把模块的分配调用引过来，
第 k 次分配返回 NULL。

注入**不等于**失败：一次 `contacts_add` 可能只要 1 次分配，也可能要 2 次
（扩容的桶数组 + 节点）。三种结果都要区分：

| 注入点 | 期望结果 | 依据 |
|---|---|---|
| 首次插入时桶数组分配失败 | 返回 `NOMEM`，`count` 仍为 0，索引仍为空 | 没有索引只能线性查重，等于把 O(n²) 还给调用方，必须上报 |
| 扩容的桶数组分配失败 | 返回 `CONTACTS_OK`，桶数不涨，装载因子超过 1.0 | 扩容是纯性能优化，不该否决合法插入 |
| 节点分配失败 | 返回 `NOMEM`，`count` 不涨，已有记录仍可查 | 失败的插入不能留下"挂上了但索引里没有"的节点 |

每个注入点检查的不是"返回值对不对"，而是六项不变量：`count`、遍历长度、
索引 `entries`、已插入姓名全部可查、查到的电话正确、未插入姓名不可查。
另外每个规模都断言"至少有一个注入点真的让插入失败了"——一个从来没生效过的
测试比没有测试更危险。

`contacts_load` 的注入是另一条：200 行文件、在第 k 次分配失败时，
必须返回 `NOMEM` 且 `skipped` 为 0。改动之前的行为是把剩余 199 行全部计入
`skipped` 再返回 `OK`——调用方看到的是"载入成功，只是跳过了一部分"，
无从区分"文件里有坏行"与"进程快没内存了"。

### 5.6 反向验证：缺陷注入

测试通过只能说明"当前实现没被这些断言抓到错"，不能说明"这些断言抓得住错"。
因此另外做了一轮缺陷注入——把实现改坏，看测试是否失败：

| 注入的缺陷 | 结果 | 抓住它的是 |
|---|---|---|
| `contacts_add` 只挂链表，不挂桶链 | 大量 `FAIL`（`能找到 alice` 实际 0 等） | 任何查找类用例 |
| `contacts_remove` 拆了链表，不拆桶链 | 普通构建 `double free or corruption` 中止；ASan 报 `heap-use-after-free`，栈顶在 `__interceptor_strcmp` | 删除后重查的用例 + ASan |
| 哈希函数恒返回 0 | `最长链不超过 20` 实际 0、`非空桶超过一半` 实际 0 | 索引分布断言 |
| 扩容时不重挂桶链 | `扩容后 entries 仍等于条数` 实际 1、`entries 等于 count` 实际 976（期望 2000） | 索引一致性断言 |

第二条值得注意：它不产生任何"结果不对"的返回码，而是让桶链指向已释放的节点。
没有 ASan 时表现为 `glibc` 的 `double free or corruption` 中止（堆元数据被写坏），
有 ASan 时定位到具体是被 `strcmp` 读取。这类缺陷只靠"功能测试全绿"是发现不了的。

### 5.7 内存与资源

| 验证项 | 结果 |
|---|---|
| ASan（越界、泄漏） | 无报告 |
| LeakSanitizer（退出时链表或桶数组未释放） | 无报告，`contacts_clear` 同时释放节点与桶数组 |
| 重复 `contacts_destroy` | 不崩溃，数量归 0 |
| 各接口传 NULL | 返回 `CONTACTS_ERR_PARAM` 或安全返回，不崩溃 |
| 保存到不可写的目录 | 返回 `CONTACTS_ERR_OPEN`，不留半成品文件 |
| 载入不存在的文件（REPLACE 模式） | 返回 `CONTACTS_ERR_OPEN`，书内容不被改动 |
| 分配失败后立即重试同一操作 | 成功，且新记录可查（无残留中间状态） |

最后一条值得说明：注入失败之后不重建 `contact_book` 就重试，是对
"失败时数据结构自洽"最直接的检验。如果 `contacts_add` 在失败前已经把节点挂上链表，
重试会得到两条同名记录或一条查不到的幽灵记录。

`CONTACTS_LOAD_REPLACE` 是**先清空再打开**还是**先打开再清空**，行为不同。
实现里先 `fopen`，成功之后才 `contacts_clear`——否则一个打不开的路径
会把现有内容清掉，用户什么都没得到还丢了数据。

```
   16000          2.4          2.0          1.2          2.6      16000
   64000         10.7          8.4          4.7         11.2      64000

       n   buckets     load  maxchain   used/buckets  find(ns)   heap(KiB)  B/entry
--------------------------------------------------------------------------------------
    1000      1024     0.98         3            68%        58         170      174
    4000      4096     0.98         7            57%        59         667      171
   16000     16384     0.98         6            64%        63        2514      161
   64000     65536     0.98         7            56%        65       10016      160
```

`find` 一列做的是 2n 次查找（n 次命中 + n 次落空），`find(ns)` 是单次平均耗时。
`heap` 是 glibc `mallinfo2` 的 `uordblks`，即已分配未释放的堆字节数；
`B/entry` 是它对条数的平均。

### 6.1 差距有多大

n = 64000：

| 操作 | 纯链表 | 加索引 | 倍数 |
|---|---|---|---|
| `build` | 5019.7 ms | 10.7 ms | **469×** |
| `find`（2n 次） | 16868.8 ms | 8.4 ms | **2008×** |
| `load` | 5358.9 ms | 11.2 ms | **478×** |
| `save` | 8.1 ms | 4.7 ms | 1.7×（噪声级别，见下） |
| 单次 `find` | 约 132 µs | 65 ns | **约 2000×** |

`save` 两列不该差这么多：它不碰索引，只是顺序遍历 + `fprintf`。8.1 ms 与 4.7 ms
的差别来自页缓存状态（两次运行之间文件刚被写过），不是实现差异。
**同一个数字变快不等于改对了**——`save` 这一列就是对照组：没有理由变化的指标也变化了，
说明这个量级的差异属于测量噪声。

真正的对照组是复杂度。看规模翻倍的增长率：

| 段 | `build` 纯链表 | `build` 加索引 |
|---|---|---|
| 1000 → 4000（4×） | 1.4 → 20.1 ms（14.4×） | 0.2 → 0.6 ms（3.0×） |
| 4000 → 16000（4×） | 20.1 → 315.3 ms（15.7×） | 0.6 → 2.4 ms（4.0×） |
| 16000 → 64000（4×） | 315.3 → 5019.7 ms（15.9×） | 2.4 → 10.7 ms（4.5×） |

纯链表每一段都是 4 倍输入、约 16 倍耗时，符合 O(n²)；加索引之后是 4 倍输入、
4 倍上下耗时，符合 O(n)。**耗时曲线比单个数字更能说明改动是否命中了目标。**

### 6.2 索引自身的形态

| n | 桶数 | 装载因子 | 最长链 | 非空桶占比 | 堆占用 |
|---|---|---|---|---|---|
| 1000 | 1024 | 0.98 | 3 | 68% | 170 KiB |
| 4000 | 4096 | 0.98 | 7 | 57% | 667 KiB |
| 16000 | 16384 | 0.98 | 6 | 64% | 2514 KiB |
| 64000 | 65536 | 0.98 | 7 | 56% | 10016 KiB |

三件事可以互相印证：

1. **装载因子稳定在 0.98**，因为扩容发生在"插入后条数 > 桶数"的那一刻，
   桶数翻倍之后装载因子立刻掉到 0.49，再随插入爬回 1.0。0.98 说明采样点在扩容之前。
2. **最长链 3~7 条**。装载因子 1.0 时随机均匀散列的最长链期望在 `ln n / ln ln n`
   附近（n = 64000 时约 10），实测 7 条说明 FNV-1a 在这批姓名上没有退化。
   如果哈希函数只用到了少数字节，这里会出现几十上百。
3. **`B/entry` 在大规模上稳定在 160 字节**，可以做算术核对：节点 `sizeof(contact)` =
   152 字节（64 + 64 + 3 个指针），桶表 65536 × 8 = 512 KiB 摊到 64000 条是 8.2 字节，
   合计 160.2 字节——与实测 160 一致，说明索引之外没有隐藏的额外分配。
   小规模时偏高（1000 条时 174），多出来的是与条数无关的固定开销：
   stdio 缓冲区、分配器元数据、以及桶表按 2 的幂增长留下的余量，不随条数增长。

### 6.3 这份代价值不值

纯链表在真机上的数字已经很清楚：六万四千条时一次查找约 132 µs，载入 5.4 秒。
这不是"稍微慢一点"，而是"这个用法不成立"：132 µs 的查找放在按键实时响应的场景里
是能感知到的延迟，5 秒的载入会让任何批量导入不可用。

加索引后的固定成本是每个联系人 8 字节（桶链指针）加约 8 字节的桶表，
相对节点本身的 152 字节是 11% 的膨胀。一千条的联系录多占 17 KiB，
六万四千条多占 1.1 MiB——对任何一种持有六万条联系人的场景都不构成约束。

范围要划清楚：**几百到一两千条时，两种方案的绝对耗时都在亚毫秒级，选哪个都行；
超过一万条，纯链表不是慢，是设计上不可用。** 索引的成本与规模线性、可预测；
纯链表的成本是平方的，无法靠等待掩盖。

### 6.4 为什么仍然要保留链表

一个自然的疑问：既然索引已经能 O(1) 定位，为什么还要链表？

因为接口有两个方向的需求，索引只解决其中一个：

- **按姓名定位**（`find` / `remove` / 查重）——索引的主场。
- **按插入顺序枚举**（`contacts_first` / `contacts_next` / `save`）——索引答不了。
  桶链的顺序是"最近插入在前"，且按桶分组；要按插入顺序输出，只能另有一个顺序结构。

链表就是那个顺序结构，而且它的成本已经被前面的改动摊掉了：追加 O(1)（有 `tail`），
遍历 O(n) 且不需要额外内存。用"桶数组 + 排序"替代链表，每次 `list` 都要 O(n log n)，
还要额外一份指针数组——用更贵的东西换更便宜的东西，没有理由。

## 7 实现记录：从菜单 demo 到模块

这个主题从一份 355 行的教学代码 `contacts.c` 开始，经过两轮改造才成为模块：

| 轮次 | 产物 | 规模 | 做了什么 |
|---|---|---|---|
| 起点 | 原版 `contacts.c` | 355 行 | 能跑，但有多处缺陷，且完全是 demo 形态 |
| 第一轮 | 同一文件的修订版 | 355 行 | 补文档、修格式描述、扩充缺陷清单 |
| 第二轮 | **本模块** | 头文件 + 实现 + 驱动 + 测试 | 接口与实现分离，修掉全部缺陷，可被独立链接 |
| 第三轮 | 本模块 1.1.0 | 同结构，实现加约 120 行 | 加哈希索引：查找/查重/删除 O(1) 均摊；补分配失败注入 |

原版源码保留在 git 历史里，可以随时取回对照：

```bash
git show 8d9c40f:04-contact-list/contacts.c > /tmp/contacts_orig.c
```

### 7.1 起点

原版是一个启动即进菜单的交互程序：`main` 里 `while (1)` 打印菜单、`scanf` 读选项、
`switch` 分派到 `insert_entry` / `print_entry` / `delete_entry` / `search_entry` /
`save_entry` / `load_entry`。所有函数都在一个文件里，所有输入都走 `scanf`。

这个结构的问题不在于"能不能用"，而在于**它没法被测试**：任何验证都只能往标准输入里
灌一串数字，菜单顺序一改，全部测试作废。

### 7.2 修掉的缺陷

| # | 缺陷 | 依据与后果 | 处理 |
|---|---|---|---|
| 1 | `char name[16]` / `char phone[32]` 偏小 | 姓名只有 15 字节可用，UTF-8 下一个汉字 3 字节，五个字就满 | 容量提到 64 / 64，并且公开成宏 |
| 2 | `scanf("%s", ...)` 无宽度限制 | `%s` 不检查目标缓冲区容量，输入超长直接越界写栈 | 驱动层改用 `fgets` + 长度校验，模块层统一走 `contacts_check_field` |
| 3 | `parser_token` 第一个循环只认逗号 | 行内没有逗号时越过 `'\0'` 继续读（`'\0' != ','`），ASan 报 `stack-buffer-overflow`，访问偏移 256 越过了 128 字节的 `buffer` | 解析器先判分隔符是否存在，长度全程有界 |
| 4 | `parser_token` 写 `name[j++]` 无边界检查 | 字段超长时溢出调用方缓冲区，ASan 实测报在 `contacts.c:123` | 解析结果先校验长度再拷贝 |
| 5 | **存取不互逆** | `save` 写 `, phone: `，解析器按"第一个空格"切，读回变成 `phone:139...`，每往返一次多一层前缀 | 统一格式 + 标签感知解析 + 入口禁止逗号，往返逐字节相同 |
| 6 | `while (!feof(fp))` | C11 7.21.10.2：`feof` 指示器由**失败的**读取设置，是事后标志，循环必然多跑一轮 | 以 `fgets` 返回值为条件 |
| 7 | `load_file` 中途 `malloc` 失败直接返回 | `fp` 永不关闭，文件描述符泄漏 | 单点关闭，所有路径都走 `fclose`，`errno` 先存后恢复 |
| 8 | 四个函数声明 `int` 却没有 `return` | C11 6.9.1p12：执行到终结的 `}` 且调用方使用返回值是未定义行为；GCC `-Wall` 直接报 `-Wreturn-type` | 统一返回 `contacts_status` |
| 9 | 退出时只 `free(cts)`，不释放链表 | LeakSanitizer 实测每条泄漏 `sizeof(struct person)` = 64 字节 | `contacts_destroy` 遍历释放，`next` 在 `free` 之前取出 |
| 10 | 头插法导致顺序反转 | `Print` 与 `save` 都是倒序，往返一次顺序又反一遍 | 维护 `tail`，O(1) 追加，顺序 = 插入顺序 |
| 11 | `count` 在载入时只增不减，追加与替换语义不明 | 同一个文件读两遍，条数翻倍且分不清哪些是新的 | `contacts_load` 显式传 `APPEND` / `REPLACE` |
| 12 | 调用方不检查返回值 | `delete_entry` 返回 -2、`insert_entry` 返回 -3，`main` 一概不理，用户看不到任何反馈 | 状态码分类 + 驱动层退出码 + 针对性提示 |
| 13 | `save_file` 每写一行就 `fflush` | 白白增加系统调用；`fclose` 本身会刷新 | 只在关闭时刷新，并改成"临时文件 + rename" |

第 5 条是这一组里最值得留意的：**它不触发任何 sanitizer**。所有缓冲区都在范围内，
没有任何越界、没有任何泄漏，但数据被悄悄改错了。这类缺陷只能靠往返测试发现，
也是"能跑"与"正确"之间最容易被忽略的那道缝。

第 3 条和第 4 条有先后关系：写越界（`contacts.c:123`）在多数输入下先触发，
把读越界（`contacts.c:119`）挡住。修完一个必须重跑，才能看到后面那个。

### 7.3 结构上的改变

| 原版 | 本模块 |
|---|---|
| 一个 `contacts.c` 包含全部逻辑 | `include/`（接口）+ `src/`（实现）+ `src/main.c`（驱动） |
| 只能通过菜单交互 | 子命令（可脚本化）+ `menu` 子命令（保留原交互方式） |
| 内部函数全部非 `static`，符号污染全局命名空间 | 公开接口 + `libcontacts.a`，`main.c` 只链接不重编 |
| 错误只能用 `-1` / `-2` / `-3` 表达 | `contacts_status` 十一种分类，附 `contacts_status_string` |
| 无限定宽度的 `scanf("%s")` | `fgets` + `contacts_check_field` |
| 手写测试，无自动化 | `make test`（584 项）+ `make check`（21 项）+ `make sanitize` |
| 手动 `gcc` 一行命令 | `Makefile`，目标拆分，零警告构建 |
| 只能统计不能测量 | `make bench` 给出四个规模的耗时、索引形态与堆占用 |

改动里最关键的一步是**把"用户输入"从模块里挪出去**。原版的 `insert_entry` 里
既有 `scanf` 又有链表插入，两件事粘在一起，导致这个函数既没法在测试里调用，
也没法在别的程序里复用。拆开之后，模块只接受"已经到手的两段字符串"，
输入怎么来、要不要提示、用什么读，全部由驱动层决定。

### 7.4 第三轮：为什么接口不用改

加索引这件事，接口一行都没动——除了新增一个诊断函数。原因是第二轮已经定下了
"接口描述行为，不描述结构"：`contacts_find(book, name)` 说的是"按姓名找到那条记录"，
不说"怎么找"。所以从线性扫描换成哈希定位，是纯实现替换。

这也解释了为什么新增的诊断接口叫 `contacts_index_get` 而不是给 `contacts_find`
加参数：把实现细节从返回值里漏出去，会让调用方开始依赖它，下次想换结构就不行了。
诊断接口是显式的例外——名字里带 `index`，语义上就写明"这是实现细节，不是契约"。

顺便修掉一处被索引问题暴露出来的缺陷：`contacts_load` 遇到 `contacts_add` 返回
`NOMEM` 时，原来把它和"坏行"归进同一个 `else` 分支，于是内存耗尽时剩余所有的行
都被计成 `skipped`，函数最后返回 `CONTACTS_OK`。在纯链表实现下这条路径几乎不可能
被触发（每次插入只分配一个 136 字节的节点，要失败早就失败了），加了索引之后
每次插入多一次桶表分配，`NOMEM` 的可能性变高，这条路径才值得认真对待。
修法不是"特殊照顾 NOMEM"，而是回到契约：**`NOMEM` 与数据内容无关，不该被
"坏行只跳过"这条规则吸收。**

## 8 文件格式规范

这一节把格式写成可以独立实现的形式——换一门语言重写读取器时，只看这一节就够。

**编码**：字节流，不做字符集转换。UTF-8 文本按原样存。

**记录**：一行一条。`\n` 或 `\r\n` 结尾都接受，读取时把行尾的 `\r` `\n` `\t` 空格一并去掉。

**字段**：一条记录由两个字段组成，用**逗号**分隔。每个字段写成 `标签冒号 值`，
字段值取冒号之后、到下一个分隔符（逗号或行尾）之间的内容，再去掉两端空白。

```
name: alice, phone: 13900001111
└─┬─┘ └─┬─┘  └─┬──┘ └────┬────┘
  │     │      │         └─ 第二字段的值
  │     │      └─ 第二字段的标签（内容不参与语义）
  │     └─ 第一字段的值
  └─ 第一字段的标签（内容不参与语义）
```

**标签**：读取时忽略内容，只认冒号。因此 `name:` / `telephone:` / `phone:` / `tel:`
都可以。写入时统一用 `name:` 与 `phone:`。

**约束**：

- 字段值不能为空
- 字段值不能含 `,` `\n` `\r`
- 第一字段长度 < 64 字节，第二字段 < 64 字节（均可通过宏调整，但读写双方必须一致）
- 单行长度不超过 510 字节（超过整行作废，不会被截断成两条）

**空行**：忽略。**无法解析的行**：跳过并计数，不中断载入。

**写出**：`name: <v1>, phone: <v2>\n`，字段值按原样写出，不做任何转义。

## 9 已知局限

### 9.1 查找是 O(1) 均摊，但最坏情形仍是 O(n)

`contacts_find` 按姓名算哈希、取桶、在桶链上比较。装载因子不超过 1.0 时平均链长
1 条多一点，实测单次 65 ns（n = 64000，第 6 节）。但要强调"均摊"两个字：
如果所有姓名都落在同一个桶上，退化成线性扫描。触发条件见 9.7。

### 9.2 索引的成本是内存，不再是时间

纯链表时代这一条写的是"批量构建与载入是 O(n²)"。加了索引之后这个局限消失了：
n 从 16000 到 64000（4 倍输入）`build` 从 2.4 ms 到 10.7 ms（4.5 倍），是线性的。
剩下的代价换成内存：每个节点多一个 `hash_next`（8 字节），加约 8 字节/条的桶表，
合计约 160 字节/条。十万条的联系录要多占约 1.1 MiB —— 可以接受，但要写清楚。

### 9.3 没有事务语义

`CONTACTS_LOAD_REPLACE` 会先清空再载入。如果载入中途出错（不是坏行，而是读错误
或内存不足），已经清掉的原内容回不来。需要"失败保持原样"的调用方应当先载入到
另一个 `contact_book`，成功之后再交换。

保存倒是安全的：临时文件 + `rename`，失败时目标文件保持原样。

### 9.4 没有并发控制

模块内部不加锁。不同的 `contact_book` 之间完全独立，可以并行使用；
同一个 `contact_book` 上的并发调用需要调用方自己加锁。

加了索引之后这一条没有变坏也没有变好：写操作仍然只改本结构内部的指针，
读操作仍然只读，因此"调用方加一把互斥锁就够了"这个结论仍然成立。
但注意 `contacts_find` 现在会读桶数组，**删节点与查找在同一本书上并发时，
拿到的指针可能是刚被释放的**——这正是需要那把锁的理由。

### 9.5 排序、分组、导入导出都未实现

当前只按插入顺序保存与输出。按姓名排序、按首字母分组、导出 CSV / vCard
都不在模块范围内，需要调用方自己做——遍历接口是游标式的，做这些事不需要模块配合。

索引不能直接用来排序：桶链的顺序是"同桶内最近插入在前"，跨桶是按下标，
与字典序无关。要排序仍然得把节点指针收进数组再 `qsort`。

### 9.6 平台相关的一处

`contacts_save` 用 `rename` 覆盖目标文件。POSIX 上是原子替换；
Windows 上同名 `rename` 会失败，需要 `ReplaceFile` 之类的接口。模块不处理这种差异。

### 9.7 哈希函数不随机化：可构造的哈希洪泛

FNV-1a 的乘数与偏移基都是固定常量，哈希值只取决于输入字节。这意味着
**可以离线算出一批哈希值相同（或落在同一个桶）的姓名**，把它们全部插入之后，
所有查找都退化成遍历那条长链——单次 O(n)，与不做索引一样慢。

这不是理论问题。2011 年 28C3 会议上的 "Hash-Flooding DoS" 之后，
Python、Ruby、PHP、Java 等语言陆续把字符串哈希改为带随机种子的版本
（SipHash 或等价的 keyed hash），就是因为这个攻击只依赖"哈希函数公开且无种子"。

本模块不做随机化的理由是场景：姓名来自本地文件或用户输入，攻击者若能把
几千条精心构造的姓名写进通讯录，他也已经能直接改文件了。**但只要输入来自不可信
来源（比如把 CSV 导入做成对外服务），这条就必须处理**。改法是在 `contact_book`
里存一个创建时取的随机种子（`getrandom(2)` 或 `clock_gettime` + PID 混合），
`hash_name` 把它混进初始值。代价是哈希结果不再可复现，测试里的"最长链断言"
要改成统计意义上的上界。

### 9.8 索引只增不减：删除不收缩

删除节点只从桶链上摘下来，不改桶数。一个装过十万条、删到只剩十条的书，
仍然占着 128K 个桶（1 MiB）。实现上做一个"装载因子低于 0.125 就减半"的收缩不难，
但收缩本身要重新分配与重挂，而"删完再删"的操作序列会让它反复收缩膨胀。
目前的取舍是：**不收缩，靠 `contacts_clear` 一次性释放。** 需要长时间持有大表
又频繁删除的场景，应当周期性重建。

### 9.9 桶数只能是 2 的幂

掩码取下标的前提。因此桶数不能按"质数翻倍"增长，装载因子会在 0.49~0.98 之间摆动，
平均约 0.73，比质数桶的 0.5~1.0 平均 0.75 差一点点——这个差别在实测里看不出来
（第 6.2 节），换来的是省掉一次整数除法。
