# thread-pool —— 固定大小线程池

预先创建 N 个工作线程，它们从一条共享的任务队列里取任务执行。
对外是一个静态库：调用方提交任务函数和参数，其余的生命周期由线程池管理。
队列可以无界，也可以给定容量上限；后者在队列满时提供两种背压方式
（拒绝 或 阻塞），把"内存无限增长"提前变成一个可处理的返回值。

线程池解决的是线程创建的固定成本问题。`pthread_create` 要做线程栈、内核调度实体、
TLS 块等一整套资源分配，实测在这台机器上"创建 + join"一个什么都不做的线程约 17 µs；
而复用已有线程完成同样一次调度大约 0.12 µs。两者差两个数量级，
所以任务量大而单个任务小时，复用是唯一可行的做法。

## 对外接口

`include/threadpool.h`。所有对象通过不透明句柄 `threadpool *` 访问。
内部要放 `pthread_mutex_t` 与两个 `pthread_cond_t`，公开它们会强迫每个调用方
`include <pthread.h>`，并把 pthread 同步原语的内部布局固定成 ABI 的一部分。

| 函数 | 作用 |
|---|---|
| `threadpool_create(nthreads, &pool)` | 创建池（队列无界），返回前 N 个工作线程已就绪 |
| `threadpool_create_bounded(nthreads, max_queued, &pool)` | 创建池，队列最多容纳 `max_queued` 个待执行任务 |
| `threadpool_destroy(pool)` | 优雅停机：排空队列 → 唤醒等待中的提交方 → join 线程 → 释放 |
| `threadpool_submit(pool, fn, arg)` | 提交任务；队列满时立即返回 `TPOOL_ERR_FULL` |
| `threadpool_submit_wait(pool, fn, arg)` | 提交任务；队列满时等待空位（工作线程不会被阻塞，见下） |
| `threadpool_wait(pool)` | 屏障：等到队列空且无人执行 |
| `threadpool_queued(pool)` | 队列中待执行的任务数 |
| `threadpool_running(pool)` | 正在执行的任务数 |
| `threadpool_completed(pool)` | 累计执行完成数 |
| `threadpool_submitted(pool)` | 累计提交成功数 |
| `threadpool_capacity(pool)` | 队列容量上限；无界池返回 0 |
| `threadpool_backpressure(pool)` | 累计"因队列满而真正进入等待"的提交次数 |
| `threadpool_thread_count(pool)` | 工作线程数 |
| `threadpool_status_string(s)` | 状态码的英文短名 |

状态码：`TPOOL_OK`、`TPOOL_ERR_PARAM`、`TPOOL_ERR_NOMEM`、`TPOOL_ERR_SYSTEM`、
`TPOOL_ERR_CLOSED`、`TPOOL_ERR_BLOCKING`、`TPOOL_ERR_FULL`。

### 所有权

这条约定决定了调用方要不要写 `free`，因此单独列出：

- **任务节点归池所有。** `submit` 内部用 `malloc` 分配节点，任务函数返回后由池释放。
  调用方拿不到这个节点，也不需要关心它。
- **任务参数 `arg` 归调用方所有。** 池把它原样转交给任务函数，不解引用、不释放，
  `destroy` 时也不会去回收未执行任务的 `arg`。需要回收就由调用方在任务函数里做，
  或者等 `wait`/`destroy` 返回后统一做。
- **池对象归调用方所有**，由 `threadpool_create` 分配、`threadpool_destroy` 释放。

### 线程模型

- `submit` / `wait` 可以从任意线程调用，包括工作线程内部（任务里再提交任务是允许的）。
- `submit` 与 `submit_wait` 在有界池上行为不同：前者满即返回 `TPOOL_ERR_FULL`，
  后者阻塞到出现空位。**唯一的例外是工作线程**：工作线程调用 `submit_wait`
  时若队列已满，直接返回 `TPOOL_ERR_FULL`，不进入等待（理由见设计要点 8.4）。
- `wait` **不能**由工作线程调用：它等的是"正在执行的任务数归零"，而调用者本身
  就是一个正在执行的任务。实现里用 `pthread_equal(pthread_self(), tids[i])` 检测
  并返回 `TPOOL_ERR_BLOCKING`，不进入等待。
- `destroy` 必须由提交方线程调用。它返回之后池对象失效，任何后续调用都是未定义行为。

## 设计要点

### 1. 两个条件变量，而不是一个

工作线程等待的条件是"队列非空或该退出"，`wait` / `destroy` 等待的条件是
"队列空且无人执行"——两者正好相反。共用一个条件变量时，每次状态变化都只能
`pthread_cond_broadcast`，否则可能唤醒错的那一类等待者，而该唤醒的继续睡着
（丢失唤醒）。broadcast 是正确的，代价是惊群：提交一个任务，N 个空闲线程全部被
唤醒抢同一个任务，其中 N-1 个重新睡回去，白付一次上下文切换。

分成 `work` 与 `idle` 之后，`submit` 只 `signal` 一个工作线程，
任务完成只在"队列空且 running 归零"时 broadcast 给 `idle`。
基准里 1 线程到 8 线程空任务吞吐从 121 ns 掉到 636 ns，说明这条路径上仍然
有共享状态竞争（单个互斥锁保护的单条队列），但至少不是每次提交都惊群。

### 2. 队列是 FIFO，不是 LIFO

单链表可以头插也可以尾插，取的时候从表头取。头插头取就是栈：最后提交的任务最先执行。
在"提交速度持续高于消费速度"的负载下，先提交的任务会被后来的不断压到队尾，
可能长时间得不到执行——这是**饥饿**，不是"顺序不同"那么轻的问题。

本实现维护 `head` 与 `tail` 两个指针，尾插入队、表头出队，得到严格的 FIFO。
代价只是多维护一个指针，收益是"提交顺序 = 执行顺序"这个可以直接写成测试的保证：

```
--- 单工作线程下的 FIFO 顺序 ---
ok    执行了 N 个
ok    执行顺序 == 提交顺序（FIFO）
```

多工作线程时只能保证**取出顺序**是 FIFO，完成顺序由调度决定——同一条队列上，
先取到任务的线程不一定先跑完。所以测试只在 1 个线程的池上断言执行顺序。

### 3. 等待条件必须写成循环

```c
while (p->head == NULL && !p->stop) {
    pthread_cond_wait(&p->work, &p->lock);
}
```

`pthread_cond_wait` 返回并不等于条件成立，有两种情况：

- **虚假唤醒**（spurious wakeup），POSIX 明确允许 `pthread_cond_wait` 在没有
  `pthread_cond_signal`/`broadcast` 的情况下返回。标准这样规定是为了允许实现
  用"唤醒后重新检查"的简单结构，因此调用方必须自己重新检查条件。
- 被 broadcast 唤醒，但队列里那个任务已经被别的线程取走了。

写成 `if` 的话，这两条路径都会让线程去取一个不存在的任务（`head == NULL` 时解引用）。

### 4. 执行阶段不持锁

工作任务从队列取走之后立刻 `pthread_mutex_unlock`，再去调用任务函数。
如果持锁执行，所有工作线程会退化成串行：一个线程干活，其余线程在锁上排队，
线程池变成"一个线程 + N-1 个等待者"，吞吐比单线程还低（多出锁竞争成本）。

代价是任务函数不能假设池的互斥锁保护着任何外部状态——它什么锁都没持有。

### 5. 优雅停机：排空队列，而不是丢弃

`threadpool_destroy` 的顺序是：

```
置 closed（拒绝新任务） → 等 queued == 0 && running == 0 → 置 stop → join → 释放
```

等待期间工作线程照常取任务（`pthread_cond_wait` 会释放锁），因此不会因为
destroy 持锁而饿死它们。

为什么不能直接丢弃队列：那样调用方既拿不到"哪些任务没执行"的信息，也没有返回值，
任务参数还留着自己手上——一个静默的、不可观测的工作丢失。库的默认行为不该是这个。
验证方式是把 200 个 1 ms 的任务提交进 1 个线程的池，然后**不等**就 destroy：
200 个任务必须全部执行完，destroy 耗时约 211 ms。

### 6. create 失败要回滚，不能留半截状态

`pthread_create` 可能因资源限制失败。此时已经创建的工作线程正在
`pthread_cond_wait` 上等任务。直接 `return` 的后果是：线程泄漏，且池对象被释放后
这些线程持有悬空指针。正确顺序与 destroy 相同——置 `stop`、broadcast、join，
最后才析构同步原语；反过来的话线程可能正在一个已销毁的条件变量上等待，
按 POSIX 是未定义行为。

### 7. `pthread_t` 只能用 `pthread_equal` 比较

`wait` 里判断"调用者是不是本池的工作线程"时，不能用 `==`：
POSIX 只规定 `pthread_t` 是"用于标识线程的不透明类型"，
没有规定它是算术类型或指针，可比较性由实现决定。Linux 的 glibc 里它是
`unsigned long`，`==` 恰好能编过；换一个实现就可能编译不过或者比错。

### 8 有界队列与背压

#### 8.1 无界队列的真实故障模式

`threadpool_submit` 从不阻塞，也不看队列长度。生产速度持续高于消费速度时，
队列长度与 `malloc` 出来的任务节点一起增长，直到某一次 `malloc` 返回 `NULL`。
那一刻的错误码是 `TPOOL_ERR_NOMEM`，出现在**任意**一次提交里——调用方通常
没有任何回退路径：任务参数已经准备好，队列里还压着几十万个没执行的任务，
程序除了退出没有别的选择。内存耗尽不是"性能问题"，它是在一个无法处理的位置
把控制流交给调用方。

有界队列把这件事提前：队列满是一个**可以预期、可以处理**的状态。两种处理方式
对应两种接口：

| 接口 | 队列满时的行为 | 适合的场景 |
|---|---|---|
| `threadpool_submit` | 立即返回 `TPOOL_ERR_FULL` | 有降级路径：丢任务、合并、写磁盘、给上游返回 429 |
| `threadpool_submit_wait` | 阻塞到出现空位再入队 | 不能丢任务，且提交方不怕慢：批处理、文件导入 |

两种都提供，是因为它们对调用方的时间语义完全不同。库只给阻塞版，会把"想丢任务"
的调用方逼成"自己开一个线程池 + 一个中转队列"；只给拒绝版，则把重试循环
（带退避、带超时、带放弃）的复杂度推给每个调用方。语义放在接口上，
调用点才是可读的。

#### 8.2 容量只约束"排队"，不约束"执行中"

`max_queued` 的判据是 `queued >= max_queued`，其中 `queued` 只统计仍在队列里、
尚未被取走的任务。所以：

```
任意时刻在途任务数 <= max_queued + nthreads
```

为什么不把正在执行的任务也算进去：容量约束的对象是**积压**，而正在执行的任务
已经出队、节点在任务返回时立刻 `free`，它不构成积压。把它算进去的后果是
`max_queued == 1` 在 4 线程池上只能有一个任务在跑，其余三个线程空转——
容量参数变成"并发度参数"，两件事被一个数字绑在一起。

这个不等式的用处是把内存上限变成可以算的数：任务节点是
`sizeof(struct task)` = 24 字节（函数指针 + 参数指针 + next），加上 glibc 的
`malloc` 块头（16 字节）与对齐，实际约 40 字节/任务。8 线程 + `max_queued = 1024`
的池，积压内存上界约 40 KiB。第 5 节有实测：同样提交 20 万个任务，
无界队列的 RSS 峰值比容量 64 的有界队列高一个数量级。

#### 8.3 第三个条件变量

前两个条件变量（`work` / `idle`）等待的方向是"队列出现任务"与"任务全部执行完"，
有界队列引入的是第三个方向：**"队列出现空位"**。

不能复用 `work`：等在 `work` 上的是工作线程，它们在等"有任务"；提交方在等
"有空位"。这两个条件在同一个状态（队列从满变成不满）下正好一个成立一个不成立，
合并就只能 `broadcast`，每次出队把 N 个工作线程全部惊醒再让它们睡回去。
`space` 只被提交方等待，出队时 `signal` 一个即可。

唤醒时机只有两处：工作线程出队之后（腾出一个位置），以及 `destroy` 置
`closed` 之后（叫醒所有人去看"池已关门"这个新条件）。提交方入队不会唤醒
同类——它自己刚占掉一个位置。

#### 8.4 工作线程永远不等待空位

`threadpool_submit_wait` 在队列满时先判断调用者是不是本池的工作线程；
是的话直接返回 `TPOOL_ERR_FULL`，与 `submit` 相同。

这条规则不是保守，而是消除一整类死锁。把任务从队列里取走的**只有**工作线程。
若工作线程允许在满队列上等待空位，就出现"消费者等待生产者生产、而生产者
就是消费者自己"的环：当所有工作线程都卡在这个等待上，没有任何线程会去消费
队列，"队列出现空位"永远不会发生。这是死锁的教科书构造——循环等待，
且每个线程占有的资源（自己这个执行者）正是别人等待的资源。

只让非工作线程等待，就把这个环切断了：等待者一定不在"唯一的资源持有者"集合里。
判定方式与 `wait` 相同（`pthread_equal` 逐个比 `tids`），复用一个
`is_worker()` 静态函数，避免两处判定逻辑漂移。

代价是：一个"父任务提交子任务"的流水线在有界池上可能拿到 `FULL`，
需要调用方自己处理。这与直接把死锁暴露出来相比是划算的交换。

#### 8.5 destroy 与阻塞中的提交方

`destroy` 的流程多了一步：置 `closed` 之后立刻 `broadcast(&space)`。
少了这一步，等在 `space` 上的提交方永远等不到空位（队列只会越来越空，
但没有任何人通知它），而 `destroy` 又在等队列排空——双方互等。

更隐蔽的是**释放时机**。被唤醒的提交方还要重新拿一次锁，才能读到 `closed`
并返回。如果 `destroy` 只看 `queued == 0 && running == 0` 就继续往下走，
它可能在对方仍持有 `p->lock` 这个地址的时候 `pthread_mutex_destroy` 并 `free(p)`；
对方随后对这块内存执行 `unlock`。按 C11 6.2.4p2，对象的生存期在 `free` 时结束，
之后任何访问都是未定义行为。这类 bug 在普通构建下经常"看起来正常"
（内存还没被复用），只有 ASan 稳定报 `heap-use-after-free`。

修法是加一个 `waiting` 计数：提交方进入等待前 `waiting++`，醒来后 `waiting--`，
并在归零时 `broadcast(&idle)`；`destroy` 的等待条件因此变成
`queued > 0 || running > 0 || waiting > 0`。这与"等待者必须在离开临界区之后
才允许销毁它使用的同步原语"是同一条规则的两种写法。

#### 8.6 被唤醒后必须重新检查 closed

`pthread_cond_wait` 返回不代表条件成立（虚假唤醒，以及被 `destroy` 的
broadcast 唤醒），因此等待写成 `while (满 && !closed)`。循环退出有两种原因，
必须分开处理：`while` 条件因 `closed` 成立而退出时，要返回 `TPOOL_ERR_CLOSED`
并且**不入队**。

漏掉这一步的后果是静默丢工作：任务被塞进一个正在停机的池，而 `destroy`
在上一步已经观察到"队列空且无人执行"，随后置 `stop` 唤醒工作线程退出。
这条任务留在队列里，没有任何线程会取它，`submit_wait` 却返回了 `TPOOL_OK`。
仓库里对"静默丢工作"的一贯立场是：宁可返回错误，也不能返回成功却什么都不做。

## 构建

```bash
cd src/thread-pool
make            # libthreadpool.a + threadpool 命令行工具
make test       # 单元测试
make check      # 命令行端到端检查
make bench      # 四组基准
make sanitize   # ASan + UBSan，产物在 bin/sanitize/
make tsan       # TSan，产物在 bin/tsan/
make clean
```

命令行工具：

```bash
./bin/threadpool run     -t 4 -n 1000 -w 0.05   # 4 个线程跑 1000 个任务，每个忙等 0.05 ms
./bin/threadpool bounded -t 4 -c 8 -n 1000 -w 0.05
                                                # 队列上限 8，用阻塞提交，输出背压次数
./bin/threadpool spawn   -n 1000 -w 0.05        # 对照组：每任务新建一个线程
./bin/threadpool help
```

`run` 与 `spawn` 用同一个任务函数、同一份工作量，可以直接对比墙钟时间。
`bounded` 与 `run` 同样共用任务函数，区别只在创建方式与提交方式，
因此两者的墙钟时间差就是背压的代价，而 `capacity=` 与 `backpressure=`
是"队列真的被卡住过"的唯一直接证据——只报耗时的话，
"提交端被挡住"与"任务本身慢"无法区分。

变体构建（`sanitize` / `tsan`）落在独立目录。原因与其它模块相同：make 判断
"要不要重建"只比较时间戳、不比较编译选项，共用 `bin/` 会留下插桩过的二进制。

1.0.0 的数字（54 项单元 + 19 项命令行）是在内网 Ubuntu 上测的。1.1.0 的用例写完之后
那台机器连不上，验证改为在 CI 里做，于是第一次真跑就抓到三处问题，全部在测试与
流水线里，实现本身一行没改：

1. **闸门的超时按错了时钟。** 闸门用 `clock_gettime(CLOCK_MONOTONIC)` 构造截止时间，
   而 `pthread_cond_timedwait` 按"条件变量自身的时钟"解释它，默认是
   `CLOCK_REALTIME`（POSIX `pthread_condattr_getclock` 的默认值）。monotonic 的值是
   "开机以来的时长"，当成 1970 年的时间点必然已经过去，`timedwait` 立刻返回
   `ETIMEDOUT`——闸门从不阻塞，退化成空操作。后果是 11 项断言在测另一种状态：
   满队列被瞬间排空、背压计数为 0、"未被放行前提交方仍在等待"变成了"已返回 OK"。
   这个错误没有任何提示：闸门看起来照常工作。
   修法是 `pthread_condattr_setclock(CLOCK_MONOTONIC)`，并让闸门记录 `timed_out`，
   在"闸门本应按住"的用例里断言它没被兜底超时放开。最后这条断言本身就是回归检查。
2. **探针的跨线程读没有同步。** `workerprobe.status` 由工作线程写，主线程在
   `sleep_ms(50)` 之后读。`sleep` 不建立任何 happens-before，两条访问仍是一次数据竞争
   （C11 5.1.2.4p25 的"冲突"定义不看实际是否交叠）。TSan 报的正是这里。改为工作线程
   release 存储 `done`、主线程 acquire 读等待它。
3. **流水线把失败吞了。** `make test 2>&1 | tee log` 的退出状态取管道最后一段
   （`tee`，恒为 0），不加 `set -o pipefail` 的话，测试失败而这一步报绿。第 1 条的
   11 项失败因此一度只体现在报告文字里，没有体现在运行结论上。

单元测试覆盖的七类行为：

| 类别 | 断言内容 |
|---|---|
| 参数与生命周期 | `create(0)` / `create(-1)` / `out == NULL` 被拒绝且不留野指针；连续 10 轮 create/destroy 无线程与内存泄漏 |
| 任务语义 | 1000 个任务各执行一次；参数按 `index*2` 正确送达；计数一致（submitted = completed = 1000） |
| 队列语义 | 单线程池 32 个任务的执行顺序等于提交顺序 |
| 并发语义 | 4 个生产者并发提交 1000 个任务，无一丢失；任务内部再提交成功且父子都执行 |
| 同步语义 | `wait` 幂等（第二次 < 50 ms 返回）；`wait` 之后池可继续使用；工作线程调用 `wait` 返回 `TPOOL_ERR_BLOCKING` 且主线程不死锁 |
| 停机语义 | 200 个 1 ms 任务提交后立即 destroy，200 个全部执行完；10 万个空任务的压力测试计数无丢失 |
| 有界与背压 | 容量 0 被拒绝；队列满时 `submit` 返回 `FULL` 且被拒任务从未执行；`submit_wait` 在满队列上确实阻塞（背压计数 +1，等待 > 30 ms）并在出现空位后返回 `OK`；工作线程在满队列上不等待、直接 `FULL` 且耗时 < 100 ms；4 个生产者 × 500 个任务的采样队列深度不超过容量；`destroy` 唤醒阻塞中的提交方并返回 `CLOSED`，已接受的任务一个不丢 |

第一次跑 TSan 时报告了一处 data race，位置在**测试代码**：

```
WARNING: ThreadSanitizer: data race
  Write of size 4 by thread T26: #0 task_mark tests/test_threadpool.c:100
  Previous write by thread T9:   #0 task_mark tests/test_threadpool.c:100
```

原因是压力测试的第二轮让 100 个任务共用同一个 `slot`，多个工作线程并发写
同一块内存。池本身没有问题，是测试把"每个任务独占参数"这条约定用错了。
改成每个任务一个 `slot` 之后 TSan 干净。这件事记在这里，是因为它说明了
一个容易忽略的点：**并发测试自己必须先没有数据竞争，否则 sanitizer 的报告
会把注意力引向无辜的被测代码。**

## 性能

下面的两组数据来自两台不同的机器，不能混着比：一台是 8 核 Ryzen 7 5700X
（1.0.0 时的内网验证机），一台是 CI 的 4 vCPU 运行器。同一组内 5 轮取最小值。

### 8 核 Ryzen 7 5700X（1.0.0）

**空任务（提交 → 调度 → 执行 → 回收），20 万个任务：**

| 线程数 | ns/任务 | 任务/秒 |
|---|---|---|
| 1 | 121 ~ 131 | 7.6 ~ 8.2 M |
| 2 | 146 ~ 154 | 6.5 ~ 6.8 M |
| 4 | 290 ~ 305 | 3.3 ~ 3.5 M |
| 8 | 637 ~ 654 | 1.5 ~ 1.6 M |

**对照：每任务新建线程再 join，2 万个任务，约 16700 ~ 17130 ns/任务。**

也就是说单线程池的调度成本约为"新建+销毁一个线程"的 **1/140**。
这个比值是线程池存在的全部理由；任务越短，比值的影响越大。

**固定工作量：每任务忙等 100 µs，共 1000 个任务：**

| 线程数 | 总耗时 | 加速比 | 效率 |
|---|---|---|---|
| 1 | 100.1 ms | 1.00 | 100% |
| 2 | 50.1 ms | 2.00 | 100% |
| 4 | 25.0 ms | 4.00 | 100% |
| 8 | 12.5 ms | 7.98 | 100% |

两个结论：

1. **空任务吞吐随线程数单调下降。** 1 线程 121 ns，8 线程 654 ns，慢了 5 倍多。
   原因不是池"变重了"，而是所有工作线程争同一把互斥锁和同一条队列的
   `head`/`tail` 指针，这些字段在同一条缓存行上，每次出队都要把该缓存行
   搬到当前核心（cache line ping-pong）。空任务时这点成本就是全部成本，
   于是负加速。**单队列 + 单锁的线程池只适合任务粒度明显大于调度开销的场景。**
2. **任务粒度足够大时接近线性。** 100 µs 的任务在 8 核上得到 7.98 倍，
   说明队列竞争在 100 µs 的尺度上可以忽略。选择线程池时真正要判断的是
   任务的平均耗时与调度成本（约 0.1 ~ 0.7 µs）的比值。

### 4 vCPU CI 运行器（1.1.0，含第 4 组）

| 线程数 | 空任务 ns/任务 | 空任务 任务/秒 |
|---|---|---|
| 1 | 173.2 | 5.77 M |
| 2 | 215.5 | 4.64 M |
| 4 | 582.7 | 1.72 M |
| 8 | 1057.3 | 0.95 M |

对照"每任务新建线程再 join"是 26867.8 ns/任务，单线程池仍是它的 **1/155**。
固定工作量那一组按 4 个物理核算：1 线程 100.2 ms、2 线程 2.00×、4 线程 3.99×，
8 线程同样只有 4.00×——线程数超过核数之后不再有收益，效率掉到 50%，
这是硬件上限而不是池的限制。

**第 4 组（背压的代价），1 个工作线程，每任务忙等 3 µs，提交 20 万个任务：**

| 队列 | 提交耗时 | 队列深度峰值 | 背压次数 | RSS 峰值 |
|---|---|---|---|---|
| 无界 | 8.5 ms | 197540 | 0 | 7092 KiB |
| 有界（容量 64） | 852.5 ms | 64 | 101409 | 1204 KiB |

这一组要回答的问题是"背压换到了什么"。20 万个任务全部堆进队列只要 8.5 ms，
代价是 7 MB 常驻内存与 19.7 万个待执行节点的积压；容量 64 之后内存降到
1.2 MiB（**5.9 倍**），队列深度被硬性卡在 64，但提交端被串行化，
整轮耗时从 8.5 ms 变成 852.5 ms。

852.5 ms 里有约 600 ms 是任务本身（20 万 × 3 µs 在单线程上的下界），
剩下的是 10 万次"入队 → 等空位 → 被唤醒"的往返。也就是说**背压不是免费的**：
它把"内存无限增长"换成了"提交端排队"，两者都表现为变慢，区别在于前者会
在某次 `malloc` 失败时突然终止，后者是可预测的延迟。选容量时要能接受这个延迟。

## 实现记录

### 模块化之前修掉的 4 处缺陷

原实现（见 `notes/threadpool_annotated.c`）有四处错误，都在这次模块化之前修正：

1. 销毁流程里写的是 `worker->terminate;` —— 读一下就丢掉的**无副作用表达式语句**，
   终止标志从未被置 1，被唤醒的线程重新检查标志后又回去等待，销毁完全不生效，
   进程永久挂住。编译器对这条语句不给任何警告。
2. `nThreadPoolPushTask` 声明返回 `int` 却没有 `return`。C11 6.9.1p12：
   在要求返回值的函数中执行到 `}` 而不返回值，若调用方使用了这个值，行为未定义。
3. 用 `memcpy` 复制 `PTHREAD_COND_INITIALIZER`。POSIX 只保证这两个宏可用于
   **静态初始化**，其内部表示由实现决定，逐字节复制不保证得到一个有效对象。
4. 销毁流程未 join 未 free，而回调函数结尾又自己 `free(worker)` —— 修一处必然触发
   另一处的双重释放。最终确定 worker 结构体归池所有，回调不再自释放。

### 这次模块化改了什么

接口层面（这是主要收益，不只是搬文件）：

| 旧接口 | 新接口 | 改的原因 |
|---|---|---|
| `int nThreadPoolCreate(ThreadPool *pool, int n)` | `tpool_status threadpool_create(int n, threadpool **out)` | 旧接口要求调用方在栈上放一个 `ThreadPool`（含 `pthread_mutex_t`），池内部再 `memset` 清零它。若该对象已经被初始化过，`memset` 会直接抹掉同步原语的内部状态。改成池自己分配，调用方不可能传进一个半初始化的对象 |
| 调用方 `malloc` 一个 `struct nTask` 并填函数指针 | `threadpool_submit(pool, fn, arg)` | 旧设计把内部数据结构暴露给调用方，还必须让任务函数自己 `free(task)` —— 任务的返回值语义变成"你必须记得释放我"，漏一个就是泄漏 |
| 无 | `threadpool_wait(pool)` | 旧实现只能靠 `getchar()` 等，程序里没有任何"任务做完了"的可编程信号 |
| `nThreadPoolDestory` 丢弃队列中未执行的任务 | `destroy` 排空队列 | 见设计要点 5 |
| 无 | `queued` / `running` / `completed` / `submitted` | 没有计数器时，测试无法断言"每个任务恰好执行一次"，只能看打印输出 |
| 每条链表都用两个宏 | 队列直接写在结构体里 | 宏在只有一个使用者时只是增加阅读成本；`LIST_REMOVE` 需要 `item` 与 `list` 同时是左值，用起来容易写错 |

`main.c` 里有一个顺带记下的标准细节：`pthread_create` 的入口类型是
`void *(*)(void *)`，而任务函数是 `void (*)(void *)`。把前者强转成后者
（或反向）是未定义行为——标准没有规定两种函数指针类型可以互相转换后调用，
返回值的传递约定可能不同。对照组因此加了一层真正的适配函数 `spawn_entry`，
而不是强转。

### 1.1.0 加有界队列与背压

1.0.0 的接口只有"提交、断言、查询"三件事，没有对积压的任何约束。1.1.0 增加：

| 新增 | 作用 |
|---|---|
| `threadpool_create_bounded(nthreads, max_queued, &pool)` | 容量上限 |
| `TPOOL_ERR_FULL` | 队列满 |
| `threadpool_submit_wait(pool, fn, arg)` | 满则等待空位 |
| `threadpool_capacity(pool)` | 读容量；无界为 0 |
| `threadpool_backpressure(pool)` | "背压生效过几次"的计数器 |

结构上的改动是加一个 `pthread_cond_t space`、两个字段（`max_queued`、`waiting`）
与一个 `backpressure` 计数器。句柄不透明，所以这次改版**没有 ABI 破坏**
（1.1.0 之前的调用方二进制仍可用，只是拿不到新函数）；`TPOOL_ERR_FULL` 是枚举的
新值，位于末尾，已有状态码的数值不变。

`backpressure` 这个计数器是被测试逼出来的，和 `contact-list` 的 `rehashes`
同一个来源：想断言"背压确实生效"，看耗时不行（提交端等 3 ms 与任务本身慢 3 ms
在外部完全一样），看内存也不行（RSS 是分配器的行为）。必须由模块自己记录
"有一次提交真的进入了等待"。它同时也是排查线上"提交为什么慢"时的第一手数据。

实现过程中有两处不改就会出错的地方，都写进了设计要点：`destroy` 必须等
`waiting` 归零才能释放池（8.5），醒来后必须重新检查 `closed` 才能入队（8.6）。
前者是 use-after-free，后者是静默丢工作——两种都不报错，只在对的天气里出错。

### 1.1.0 的验证通道：从内网机器换成 CI

1.1.0 的代码写完之后，原本用来验证的内网 Ubuntu 机器连不上了（本机换了网段，
到那台机器的地址没有路由）。同时本机没有任何 Linux 工具链：Windows 上的编译器

于是把验证搬到 GitHub Actions：`.github/workflows/ci.yml` 在 `ubuntu-22.04` 上跑

## 已知局限

- **单一全局队列 + 单一互斥锁。** 空任务吞吐随线程数下降（见性能第 1 条）。
  真正的解决办法是分片队列（每个工作线程一条）配合 work stealing，
  本轮没有实现。
- **无界队列仍是默认值。** `threadpool_create` 的队列没有上限：提交速度持续高于
  消费速度时，队列与任务节点占用的内存线性增长，直到 `malloc` 失败。要背压必须
  显式用 `threadpool_create_bounded`；模块不替调用方决定容量，因为容量取决于
  任务耗时、可接受延迟与可接受内存，这三者只有调用方知道。
- **阻塞提交没有超时。** `threadpool_submit_wait` 等到出现空位为止。若消费端被
  一个永久阻塞的任务卡住（例如任务在等一个不会到来的网络包），提交方会一直等下去。
  容量与任务耗时只能给出期望值，不构成上界；需要上界得调用方自己在外面套一层定时器
  或改用 `threadpool_submit` 加重试预算。
- **等待空位的唤醒顺序没有保证。** 多个提交方同时等 `space` 时，
  `pthread_cond_signal` 唤醒哪一个由实现决定（POSIX 只说"至少唤醒一个"，
  glibc 实践上偏向等待最久的，但不构成约定）。因此最坏情况下某个提交方会比其他
  提交方多等若干轮。要严格公平需要显式的票据队列，代价是每个提交都要多一次入队。
- **`destroy` 没有强制版本。** 它一定等队列排空；若某个任务永久阻塞，
  `destroy` 就永久阻塞。没有超时参数，也没有"取消队列中剩余任务"的接口。
- **`destroy` 不能从任务函数里调用**，否则它在等 `running` 归零，而自己就是其中之一。
  这一点没有像 `wait` 那样做运行时检测（`destroy` 返回 `void`，无法上报错误）。
- **`wait` 不是栅栏。** 它只保证"调用之前已提交的任务"都完成；返回之后
  别的线程再提交的任务不受约束。
- **没有优先级、延时任务、任务取消。** 队列只有一种语义。
- **每个池独占自己的线程。** 一个进程里开两个 8 线程的池就占 16 个线程，
  没有全局线程数上限或线程共享。
